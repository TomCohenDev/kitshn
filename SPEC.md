# KitSHn 2 spec

KitSHn 2 runs your apps, sites, pages, files and machines on Cloudflare, and decides who may open each one. It puts everything on one map. Circles on the map say who. A card inside a circle is shared with that circle.

The repo is named "KitSHn 2". "kit" is the short name of the project. Code, packages and the MCP tools use `kitshn`. The CLI is `kitshn`, with `kit` as a short alias. The admin and the map live at `kit.yarden-zamir.com` (K-1208).

Requirements have stable numbers with the prefix `K-`. Do not renumber them. Mark a removed requirement "Removed" and keep its number. `VERIFY:` marks a Cloudflare fact that the docs do not confirm; the first milestone that needs it tests it.

The architecture, the request paths and the budget are in [docs/architecture.md](docs/architecture.md). The order of work is in [docs/migration.md](docs/migration.md).

## Core rules

- **K-001** The app and what it needs to deploy live in its repo. The places (machines, the Cloudflare account, domains, who may open what) live in kitshn, never in the repo.
- **K-002** "Create a repo, push, and it deploys" stays true. A new app repo needs a recipe and a workflow file, and nothing else: no per-repo secret, no setup step in kitshn. The one exception is the first deploy of a repo, which waits for one click by the owner or by an agent key that may add apps (K-819).
- **K-003** kitshn runs on Cloudflare only. Its logic and state run in one Worker with one Durable Object. Machines do only machine work: tunnels, local sites, Compose deploys, commands and builds.
- **K-004** kitshn fits the Cloudflare free plan for the setup of K-1301. A paid plan only raises limits; no feature needs it.
- **K-005** kitshn knows nothing about T3 Code. T3 Code and other programs add their own resource kinds through the local interface of section 7.
- **K-006** Every unexpected state fails closed: a request that kitshn cannot decide gets no access, and the error says why.

## Terms

- **Owner:** the person who installed kitshn. The owner is the first member of the "Owner" circle.
- **Circle:** a named group of who: people (emails), email domains, devices, networks (IP ranges), machines, and the flag "needs passkey". A circle has a default level.
- **Resource:** something that kitshn can share: a machine, a site, a page, a file, an app, a thread. Each resource kind names its levels.
- **Card:** a resource on the map.
- **Share:** a card inside a circle. It gives the members of the circle the circle's default level on that resource, or the level of an override.
- **Level:** what a share allows. Each resource kind names its own ordered levels, for example `view`, `use`, `control`.
- **Daemon:** the `kitshn` program on a machine.
- **Provider:** a program on a machine that adds resource kinds through the daemon, for example T3 Code.
- **Recipe:** `kitshn.config.ts` in an app repo.
- **Environment:** one deployed copy of an app, for example `prod` or `pr-12`.
- **Job:** one piece of machine work, for example a Compose deploy.

## 1. Identity and login

- **K-101** Cloudflare Access does every login. kitshn has no login code and no password store.
- **K-102** People log in with the Access One-time PIN (an email code). GitHub is a second login method next to the email code. The passkey check of K-103 applies after either login method.
- **K-103** A circle with "needs passkey" asks for a passkey or a security key after the login, through Access independent MFA. [Independent MFA](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/independent-mfa/) supports biometrics (Touch ID, Face ID, Windows Hello) and security keys, per application and per policy.
- **K-104** kitshn administration is a resource of kind `kitshn.admin` with the level `control`. Its card sits in the "Owner" circle. The Owner circle has "needs passkey" on.
- **K-105** kitshn refuses every change that leaves the admin resource without a share to a circle that has at least one person and "needs passkey". This guard runs on every write: a drag, a circle edit, an undo, an agent tool and the pause (K-1504). It also refuses a share of the admin resource with a circle that has "everyone", because that circle compiles to an Access Bypass policy.
- **K-106** A device proves itself with an Access service token: one token per device, for example "Mac desktop app" or "Yarden's phone". A device is a circle member like a person.
- **K-107** A machine proves itself with its own service token (K-602). A machine is a circle member too, so a share can give one machine access to another resource.
- **K-108** Browser approvals of the machine map (browser keys, the Clients approval flow) do not exist in kitshn. A passkey or a device token replaces them.
- **K-109** Access sessions of the admin resource last 24 hours. Sessions of other resources last 30 days unless a circle sets a shorter time.
- **K-110** "Sign out everywhere" ends every Access session of every application that kitshn made, through the Cloudflare API. It does not end sessions of other applications (K-408). The Worker also refuses page and file logins from before the sign-out (K-1004).
- **K-111** Zero Trust Free counts one seat per person who logs in, up to 50. kitshn turns on seat expiration in Zero Trust admin controls, set to 1 month, so guests who stop coming free their seat. [Seat management](https://developers.cloudflare.com/cloudflare-one/team-and-resources/users/seat-management/) runs the expiry once a day.
- **K-112** The admin view shows the seats in use, with a warning at 40. The view can also remove a seat. Checked on 2026-10-27: `GET /accounts/{id}/access/users` lists each user with `seat_uid` and `access_seat`. VERIFY: the [seat API](https://developers.cloudflare.com/api/resources/zero_trust/subresources/seats/methods/edit/) `PATCH /accounts/{id}/access/seats` turns a seat off. Milestone 2 tests it with the Seats view.
- **K-113** Every person in a circle with "needs passkey" can open the App Launcher, because Access enrolls a passkey there (`https://<team>/AddMfaDevice`). kitshn keeps one reusable policy "kitshn passkey enrollment" on the App Launcher application, made from the emails and domains of the passkey circles with "any" match that have not ended; during a pause (K-1504), only of the Owner circle. A circle with "all must match" is left out, because its rules joined with "or" would let in more people than the circle does. A failed write of the App Launcher waits for the daily retry. It adds that policy next to the existing policies of the App Launcher and never changes or removes another policy there. The daily compare (K-408) repairs it. The circle editor shows the enrollment address while "needs passkey" is on.

## 2. Circles and shares

- **K-201** A circle has a name, a colour, a default level, members, a match mode (K-203), an optional end date, and the flag "needs passkey".
- **K-202** Member kinds: an email, an email domain, an IP range, a device token, a machine, and "everyone". "Everyone" means anyone who can reach the address, with no login.
- **K-203** A circle has one of two match modes:
  - "Any" (the default): the visitor matches at least one member. In Access, the members are include rules.
  - "All must match": the visitor matches every member, for example the domain `qlik.com` and the IP range of the Qlik network. In Access, the members are require rules. This replaces the "required IP ranges" of the machine map Guests view.

  With "needs passkey", the visitor must also pass a passkey check in both modes.
- **K-204** A card is shared with every circle that it sits inside. Circles overlap freely, and there is no limit on their number.
- **K-205** A share uses the default level of its circle. One card can override the level for one circle. The override shows as a chip on the card.
- **K-206** A level that the resource kind does not have becomes the highest level of that kind that is lower. A circle with the default `control` thus gives a file `view`.
- **K-207** When several circles match a visitor, the visitor gets the highest level of those shares.
- **K-208** A card outside every circle is private. Only the admin (K-104) can see it in the map.
- **K-209** A share can have an end date. At the end date, kitshn moves the card out of that circle as a new revision, and the history names the expiry.
- **K-210** A circle with "everyone" asks for confirmation the first time that a card enters it: "This makes <name> public."
- **K-211** The Owner circle and the Everyone circle exist from the start. The owner can rename them, and cannot delete the Owner circle.

## 3. Resources

- **K-301** Built-in resource kinds and their levels:

  | Kind | Levels | What it is |
  | --- | --- | --- |
  | `kitshn.admin` | control | kitshn administration (K-104) |
  | `machine` | view, use, control | a machine with a daemon (section 6) |
  | `site.static` | view | a static site on Workers static assets |
  | `site.worker` | view | a Worker app |
  | `site.compose` | view | a Compose app on a machine |
  | `site.live` | view | a local site of a machine, through its tunnel (K-1104) |
  | `page` | view | an HTML page in the library (section 10) |
  | `file` | view | a file in R2 |
  | `repo` | view | a repo that has a recipe; its environments are its children |

- **K-302** A provider adds kinds through the daemon (K-704). Each kind has an id with the provider prefix (for example `t3.thread`), its levels, and how it is enforced (K-405).
- **K-303** An environment of an app is its own resource and its own card, for example "riffle" and "riffle pr-41". New environments start in the circle that the recipe names (K-807).
- **K-304** Each resource has an id, a kind, a name, an owner machine when it has one, its addresses, and its status. The status is one of: running, stopped, deploying, failed, offline, unknown.

## 4. Enforcement

- **K-401** kitshn compiles shares into Cloudflare Access wherever Access can check them, so a check costs no Worker request.
- **K-402** Each circle becomes reusable Access policies: one for its people (Allow, with the passkey check), and one for its devices and networks (Service Auth), because Access lets service tokens and logins without a person in only through Service Auth. A resource with an address becomes one self-hosted Access application whose policies are the circles that hold it. Checked on 2026-10-27: the API attaches one reusable policy to two applications, and the policy reports `app_count` 2. The account limits are 500 applications and 500 reusable policies ([account limits](https://developers.cloudflare.com/cloudflare-one/account-limits/)).
- **K-403** A resource inside "Everyone" gets a Bypass policy, or no Access application.
- **K-404** The Worker checks shares itself for what it serves: pages and files (section 10 and 11). It reads the Access JWT and the visitor IP; its only cookies of its own hold the Access tokens of the login steps and the return mark of a login step (K-1004).
- **K-405** A provider enforces levels inside its own program. kitshn gives it a grant table for each of its resources (K-706). Access still guards the address: it lets in every circle with a level above none.
- **K-406** kitshn writes Access changes in a Durable Object alarm queue. One alarm run makes at most 40 Cloudflare API calls and sets the next alarm when work remains. The free plan allows 50 subrequests per request ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)).
- **K-407** The map shows a change at once. Each card shows "applying" until Cloudflare has the change, and "failed" with the reason if Cloudflare refuses it.
- **K-408** A daily alarm compares Access with the shares and repairs differences that kitshn made. It never changes an Access application or policy that kitshn did not make, and it names such an application when it covers a kitshn address. The one exception is the login applications of pages and files: kitshn removes every policy there except its own and the machines policy (K-1004).
- **K-409** A lower level takes effect at once: kitshn revokes the Access sessions of the affected application, and providers end the sessions of members that lost a level.
- **K-410** Removal order: kitshn never deletes an Access application while a route can still reach its address: tunnel ingress, a DNS record, a Worker route or a custom domain. It takes the route off and confirms it, then the DNS record, and deletes the Access application last. A failed step stops the sequence and retries after five minutes.

## 5. Map UX

The map is the main view. These requirements improve the demo of 2026-10-26.

- **K-501** The map shows every card and every circle. A toggle for each kind hides that kind. Hidden kinds still count for their circles.
- **K-502** A drag of a card, or of a selection, into or out of a circle shows a preview before the drop: each circle edge lights up, and a label says what changes, for example "+ Qlik · view" or "− Her". The drop applies it.
- **K-503** After each drop that changes a share, a toast names the change and has Undo for 10 seconds. Undo is also in the history (K-1502).
- **K-504** A drag of a circle by its head moves its cards with it. Alt and a drag moves the circle alone. The preview of K-502 then names every card that gains or loses the circle.
- **K-505** A resize of a circle shows the same preview as K-504 before the release.
- **K-506** A circle shows its members as chips on its edge, at most 4. A "+N" chip opens the full list.
- **K-507** A card shows a dot for each circle that holds it, and a chip for each override (K-205). A hover on a dot names the circle and the level.
- **K-508** Cards stack by group: the environments of one app, the pages of one thread, the files of one upload. A stack shows the top card and a count. A click spreads it in a row. A drag of a stack moves all its cards.
- **K-509** New cards arrive in a tray at the edge of the map, outside every circle, so they start private (K-208). Cards that a recipe places (K-807) and files dropped on the map (K-1101) skip the tray. The tray lists every such card, newest first, with a filter, and scrolls on its own. A card dragged from the tray, or several picked with Shift, lands where it is dropped, in exactly the circles there (K-204, K-210).
- **K-510** Multiselect: a box drag on empty space, Shift and a click, and "Select all of this kind" in the context menu. A selection moves as one.
- **K-511** The command palette (Cmd+K or Ctrl+K) finds every card, circle and action. "Share <card> with <circle>" works without a drag, also on a phone.
- **K-512** The card panel shows who can open the card: each circle, its members, the level, and the address. It has "Copy address" and "Open".
- **K-513** Zoomed out under 40%, cards become dots and each circle shows its counts by kind. The map never animates continuously, and a change plays at most one short transition.
- **K-514** Pan, zoom, fit and auto layout work as in the machine map (MM-1111, MM-1114 to MM-1121). Each device keeps its own view in local storage. On a wide screen the fit and a saved view zoom out no further than 0.85, so card names stay readable; a larger map is centred, and the wheel zooms out further.
- **K-515** A card of an offline machine, or of an app on it, shows the "offline" sticker and the time since it was last seen.
- **K-516** The map works on a phone: a long press starts a drag, and the panel is a bottom sheet.
- **K-517** The map uses the tick3d look in light and dark mode (the `neo-brutalism` skill): lilac dotted canvas, ink borders, hard shadows, tilted stickers, Bricolage Grotesque.
- **K-518** Map state (places, circles, members, shares, stacks) lives in the kitshn database, never in Git (K-001).
- **K-519** Views next to the map: History (with presets, K-716), Queue, Inbox (K-1607), Seats, usage, Machines (a table of status), Health (alerts and charts, K-1604, K-1605), Settings (K-1613), Tasks (K-1614), Clients (K-1602), Library (section 10). Each view and each selected item has its own link.
- **K-520** "Previews" shows a live view of up to four site and page cards near the centre of the map, from zoom 80%. Each is a lazy, sandboxed frame that takes no clicks until "Interact". A site behind Access shows only when the browser has its Access session already, because the Access login refuses to load in a frame; the card offers "Open site" to log in.
- **K-521** The owner can stack cards: drop a card on another card, or select several cards and choose "Stack". A stack has a name and holds two or more cards; a card is in one stack at most. Its cards sit on one point, so the stack moves as one and every card of it gets the same circles; moving one card moves its stack. A level override (K-205) and an end date (K-209) stay per card; when a stacked card's share ends, the card leaves its stack. Closed, a stack is one card that lists its cards from top to bottom; a click opens it as a column of cards. Stacks by group (K-508), such as the previews of an app, stay as they are.
- **K-522** The stack panel renames the stack, pulls one card out (it lands next to the stack, in the same circles, so no share changes), and "Unstack" spreads all cards in the same circles. Each of these, and a drop that makes or grows a stack, is one revision with Undo (K-1502); a stack that enters a public circle asks first (K-210). A drop from the tray never stacks, and a stack by group dropped on a card joins that card's stack. While a drag is over a card, the card is outlined and the label says "Stack with" it.

## 6. Machines and the daemon

- **K-601** Each machine runs one `kitshn` daemon as a service of the user who joined it: a systemd user service on Linux (it starts without a login when the user has lingering on), a launchd agent on macOS. The daemon is one binary per platform, so a machine needs no Node.js. The first version has no Windows daemon. A Windows machine stays on the machine map portal until a later milestone ([docs/migration.md](docs/migration.md)).
- **K-602** "Add machine" creates a service token and a remotely managed tunnel, and shows a one-time join command with a code that expires after 10 minutes: `curl -fsSL <address>/join | sh -s -- <code> <address>`. The command downloads the daemon, runs `kitshn join`, and starts the service. `kitshn join` saves the token and the tunnel token in a file that only the daemon user can read. kitshn stores the two tokens only encrypted with a key from the code, and deletes them when the code is used. The join exchange limits attempts per address.
- **K-603** The daemon runs `cloudflared` for the tunnel of its machine. kitshn owns the tunnel ingress through the API; the daemon never edits it. Each ingress rule whose address has a kitshn Access application sets `originRequest.access` with `required: true`, the team name (the first label of `ACCESS_TEAM_DOMAIN`) and the audience tag of that application, so `cloudflared` drops a request without a valid Access JWT ([origin parameters](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/origin-parameters/#access)). This guards the address when a DNS record or a removal step goes wrong. A rule whose application has a Bypass policy (K-403) gets no check, because Access issues no JWT for Bypass. kitshn takes this decision from the application that Cloudflare last accepted, not from the shares, so the check never comes on before Access stops the Bypass. When kitshn does not know the accepted body of the application or of one of its policies, the rule goes without the check. kitshn stores the audience tag of each application. Before it writes ingress, it reads missing tags from the list of applications, and tries again after five minutes. When the list does not have the application, kitshn forgets its id and makes it again. A site never leaves the tunnel for a missing tag: while kitshn does not know the tag, the rule goes without the check, and kitshn logs the address. An empty `ACCESS_TEAM_DOMAIN` has the same effect. The check comes on at the next tunnel write after kitshn stores the tag. Checked on 2026-10-27: a Service Auth policy whose only include is an IP range let a request from that IP in with no login, and Access set `CF_Authorization` on the response. So Access issues a JWT for a network member, and the check stays on. An Allow policy with only an IP range sends the visitor to the login instead; kitshn does not compile networks to Allow (K-402). A service token gets a JWT (K-1004).
- **K-604** The daemon keeps one WebSocket to the Durable Object at `/connect`, with backoff after a failure. Liveness uses `ping` and `pong` with the Durable Object auto response, so a ping wakes nothing.
- **K-605** The daemon sends its status on connection and on each change, at most once every 5 seconds. It sends a resource sample (CPU, memory, disk) once a minute.
- **K-606** The Durable Object keeps only the latest sample of each machine, in memory. The daemon keeps 30 days of history on its disk and answers a history request. This keeps the daily writes low (K-1302).
- **K-607** Local sites use Unix sockets. A Compose service listens on `<deployment>/sockets/<name>.sock`, and the tunnel ingress sends its address to `unix:<path>`. Services publish no host ports. Caddy is not needed. The [ingress docs](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/configure-tunnels/local-management/configuration-file/) show `service: unix:/path` for local configuration files. Checked on 2026-10-27: the API accepts `service: unix:/path` in a remotely managed tunnel configuration, and `cloudflared` 2026.10.3, run with the tunnel token, served a request from a Unix socket.
- **K-608** For an app that cannot listen on a socket, the recipe names a port inside its Compose network, and the daemon adds a small socket proxy service. The machine still publishes no host port.
- **K-609** Each machine has labels, for example `docker`, `server`, `arm`, `laptop`. The owner sets one order of all machines.
- **K-610** A job names the labels that it needs. kitshn gives it to the first online machine in the order that has all of them. Without such a machine, the job waits in the queue until its expiry (K-613). A deploy runs only on a machine that has the label `deploy`, so the apps of repos never land on a machine that the owner did not offer for them.
- **K-611** A running app stays on its machine. kitshn never moves it by itself. "Move to <machine>" in the card panel deploys it on the other machine and then removes the old copy.
- **K-612** Commands are jobs too. Built-in commands: restart the daemon, update the daemon, collect diagnostics, run a shell command. A provider adds its own commands (K-707).
- **K-613** A job for an offline machine waits. It has a delivery rule ("when online" or "when online and idle") and an expiry, by default 24 hours.
- **K-614** "Run a shell command" needs `control` on the machine. The member that sends it is in the history. A job that kitshn makes itself, such as a deploy (K-812), needs no member; the `deploy` label is the owner's consent (K-610).
- **K-615** "Remove machine" deletes its service token, its tunnel, its DNS records and its queue. Its apps show as stopped with "Deploy elsewhere".
- **K-616** A whole machine can belong to another person. Example: a second VPS whose card sits in the circle "Her" with `use`, and in the Owner circle with `control`. Its provider shows everything on it to every member with `use`, including the owner's threads there. The owner accepted this.
- **K-617** kitshn names one release: the version of its Worker. The join command, "Update daemon" (K-612) and the deploy workflow download the daemon and the CLI only from that release, `edge-<version>`, and check each file against its `SHA256SUMS`. "Update daemon" in the machine panel and the jobs API take no version from the sender. The rolling `edge` release only serves the bootstrap of a new account. The daemons are gzipped in the release (`kitshn-<os>-<cpu>.gz`), and `SHA256SUMS` names the `.gz` files. The release workflow never deletes an `edge-<version>` release: on a public repository they cost nothing, an old one is the way back, and a machine pinned to it keeps working. Every `edge` release is a pre-release, so none shows as "Latest".

## 7. Local interface for providers (T3 Code)

- **K-701** The daemon listens on a local Unix socket: `$XDG_RUNTIME_DIR/kitshn/kitshn.sock` on Linux, `~/Library/Application Support/kitshn/kitshn.sock` on macOS. Only the user of the daemon and members of the `kitshn` group can open it.
- **K-702** The socket speaks JSON lines: requests with an id, answers with the same id, and events with no id. The schema is TypeScript types with Effect Schema, published as the npm package `@kitshn/local`. Providers import the types; the daemon checks each message against them.
- **K-703** The interface pushes events. A provider subscribes once, then gets each change of its resources, grants and commands as an event. Nothing polls.
- **K-704** `register` names the provider, its resource kinds (K-302) and its commands. Each new connection registers again, so a provider restart needs no cleanup.
- **K-705** `upsert` and `remove` add, change and remove resources of the provider's kinds, with a name, a parent, addresses and a status.
- **K-706** For each resource of a provider, the daemon pushes a grant table: each circle with its match mode (K-203), its rules (an email, a domain, an IP range, a service token client id, a machine id) and its passkey flag, with its level and its end date (K-209), so the provider ends the sessions of a member at an end date by itself, also while kitshn is out of reach. The provider decides a level with no call, from the JWT that Access put on the request. The provider saves the revocations that a lower level or an end date needs, runs them again until they work, and runs them after a restart (MM-1306).
- **K-707** The daemon passes a command for a provider as an event. The provider answers with the result. The daemon forwards it to kitshn.
- **K-708** `publishPage`, `publishFile` and `expose` let a provider add a page (section 10), a file, or a live site (K-1104) with one call.
- **K-709** A resource kind can carry a desired state: a JSON value that kitshn stores and pushes to every machine with that provider. kitshn does not read the value. T3 Code uses it for shared settings and themes. Each value is at most 64 KB. A value can hold a shared part and one part per machine; kitshn pushes each machine only the shared part and its own part. A provider may send a JSON Schema of the value with `register` (K-704), so the map edits it with generic controls without knowing the provider.
- **K-710** A local round trip (request to answer) takes under 5 ms, and a change on the map reaches a provider in under 1 second when its machine is online.
- **K-711** The provider holds no Cloudflare credential. Only the daemon holds the machine token.
- **K-712** T3 Code side: the fork adds the interface in its own files, with one-line hooks in upstream files. It never breaks upstream code paths when the daemon is missing: then T3 Code runs as upstream.
- **K-713** T3 Code adds these kinds through the interface:

  | Kind | Levels | Notes |
  | --- | --- | --- |
  | `t3.app` | view, use, control | The T3 web app, desktop app connection and phone app connection of one machine. Levels map to the T3 scopes `read`, `standard`, `admin` of MM-302. |
  | `t3.thread` | view, send | One thread through upstream guest links. The circle is the guest list. |
  | `t3.agents` | use, exec | What agents on another machine may do on this machine. A machine member of a circle gets it. `use` means agent tools; `exec` adds `kitshn_exec` (MM-1908). |
  | `t3.settings` | none | Shared settings and themes as desired state (K-709). Not shareable; the map hides it. |

- **K-714** The T3 fork MCP tools get new names:

  | Machine map tool | kitshn tool |
  | --- | --- |
  | `machines_read` | `kitshn_read` |
  | `machines_set_access` | `kitshn_share` (put a card in or out of a circle, with a level) and `kitshn_circle` (create or change a circle) |
  | `machines_set_setting` | `kitshn_set_setting` |
  | `machines_command` | `kitshn_command` |
  | `machines_queue_cancel` | `kitshn_queue_cancel` |
  | `machines_undo` | `kitshn_undo` |
  | `machines_preset` | `kitshn_preset` (save, list or apply a preset, K-716) |
  | `machines_join` | `kitshn_join` |
  | `machines_resources` | `kitshn_resources` |
  | `machine_exec` | `kitshn_exec` |
  | (new) | `kitshn_publish` (page, file or site), `kitshn_expose` (a live site), `kitshn_deploy` (run a deploy) |

- **K-715** Agents never raise access. An agent change that adds a card to a circle, raises a level, or adds a circle member becomes a proposal for the owner. Changes that lower access apply at once. This keeps MM-803. For agents on a machine, K-1612 applies.
- **K-716** A preset is a saved map layout: the circles, their members and the shares, with a name. Apply a preset from the History view or with `kitshn_preset`. An apply is one revision with Undo, runs the guard of K-105, and follows K-715 for agents.
- **K-717** Each `t3.app` card has the setting "Update channel": `nightly` (a build for each commit) or `daily` (one release a day). Every machine starts on `nightly`. The setting belongs to one card, not to the kind (K-709 holds values for all machines of a kind): kitshn stores it with the card and pushes it only to the provider on that machine. Changing it needs `control` on the card, which kitshn checks when it writes the value; an agent with `control` may change it, because it does not change access (K-715). The owner changes it in the card panel or with `kitshn_set_setting`. The T3 updater uses the new channel from its next update check. Milestone 5 adds the setting; milestone 6 turns it on with the provider.
- **K-718** An agent key is a device member (K-106) without the admin card. Put it in a circle such as "Agents" and drag in the cards it may manage. Its agent circles are circles of devices only that name it, have not ended and that it matches; a circle with people, domains, networks or Everyone is never an agent circle, and a token without an agent circle gets a refusal. It manages a card that one of its circles holds at the circle level `control` (or a `control` override), before the kind cuts the level down (K-206). With its service token on `kit.<zone>/agent` it sees only those cards, without their machine or group, and its agent circles, with no members, and Everyone when it may publish; it moves those cards, but only between its agent circles at the level `control`, or out of every circle; and it runs jobs on a machine only when it manages the machine card, every card that runs on it and every card that the machine's own token opens (K-107, K-614), never by labels, checked again when a job goes out; a redeploy that it asked for goes out only while the key manages the card, the machine has the label `deploy` and runs the card; it reads the state and output of its own jobs, and the history names it by its member name. It deploys a card it manages in two ways, and never sends code itself (K-812): "redeploy" starts the last build of a Compose app that came up, from the copy that the daemon keeps on the machine, while that machine still has the label `deploy` and still runs the card; "build" runs the repo's own `kitshn.yml` workflow with `workflow_dispatch` on the branch of the environment, through the kitshn GitHub App (K-908) with a token for that repo and Actions only; a preview (`pr-<n>`) gets no such build. A dispatch deploys as a push of that branch. Both ways follow the repo gate (K-819). It never edits circles, members, stacks, levels, the pause or any admin setting. The owner gives a key two rights on its device member in an agent circle, and both are off by default: "may add apps" lets it allow a waiting repo (K-819), and "may publish" lets it publish a card of a repo that it allowed. Only a member with control on the admin card (K-104) sets them, in the circle editor; each change is a History revision that names the right, the key and the circle. The map shows them as "adds apps" and "publishes" stickers on the device in an agent circle. A publish moves a static site, Worker site or Compose app into the overlap of an agent circle of the key at `control` and the Everyone circle (`POST kit.<zone>/agent/publish` with `{"card": <id>, "public": true}`), so the key keeps managing the card: it still redeploys it, takes it back and runs jobs on its machine. Everyone counts only while it is public, has no other member and matches "any". kitshn refuses a publish that leaves every agent circle of the key at `control`; when no such circle overlaps Everyone, the owner moves the Agents circle alone (K-504) so it overlaps Everyone, and its cards stay in place. A live site is never published. `"public": false` takes the card out of Everyone and keeps it in the same other circles; this needs no right, because it lowers access. For a card outside Everyone it does nothing. A move with `/agent/apply` follows the same publish rules. This is the one exception to K-715: the owner chose the cards, the circles and the rights, so a move between them raises no access that the owner did not give. The map marks a device that has an agent circle and no admin card with an "agent" sticker.

## 8. Recipes and deploys

- **K-801** A recipe is `kitshn.config.ts` with `export default defineApp({...})`. The value is one object literal. The `kitshn` npm package exports `defineApp` and its types as a `.d.ts` with no imports, so an editor shows recipe mistakes; it has no runtime dependencies, because its CLI is one bundled file. Until it is on the npm registry, an app does not need it: Actions runs `kitshn check` from the release. For editor types, install the `kitshn.tgz` asset of an `edge-<version>` release without saving it (`npm i --no-save <address>`). A later `npm i` removes it again, so an app keeps `kitshn.config.ts` out of its own `tsc` run.
- **K-802** Recipes do not compute. A lint rule in `kitshn check` refuses loops, conditions, function calls other than `defineApp`, and imports other than `kitshn`. The lint rule is enough, because kitshn never runs repo code (K-803).
- **K-803** GitHub Actions reads the recipe without running it: `kitshn check` turns the literal object into JSON. kitshn checks the JSON with the same schema. kitshn never runs repo code. The reusable workflow is `.github/workflows/kitshn2-deploy.yml` in this repo.
- **K-804** Kinds: a Compose app (`compose`), a static site (`static`), a Worker app (`worker`). A recipe has exactly one kind.

  ```ts
  import { defineApp } from "kitshn";

  export default defineApp({
    compose: { runsOn: ["docker", "server"] },
    deploy: [
      { on: "push", branch: "main", name: "prod", address: "riffle.example.com" },
      { on: "pull_request", name: "pr-{pr}", ephemeral: true, startsIn: "Owner" },
    ],
  });
  ```

- **K-805** A static site names a build command and an output folder. Actions builds it and uploads the files. kitshn deploys them as Workers static assets, with no Worker code, so their requests are free ([static assets billing](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)).
- **K-806** A Worker app names its `wrangler.jsonc`. kitshn refuses fields that name a place: `account_id`, `name`, `routes`, `env`, and fixed storage ids. kitshn sets the name, the routes and the storage for each environment.
- **K-807** `deploy` maps triggers to environments as in KitSHn 1: the first matching entry wins. `startsIn` names the circle of a new environment, except for a repo that an agent key allowed (K-819). After that, the map decides (K-518). A `pull_request` entry is named `pr-{pr}`, and the number comes from the signed GitHub token, so a pull request reaches only its own preview. The token of a closed (merged) pull request names no number; then kitshn takes the request's number only to close a preview that the token's own head branch deployed. A push environment deploys only from the branch that first deployed it.
- **K-808** `needs.vars` and `needs.secrets` list names. Values come from the kitshn store, per app and environment. A `KITSHN_<NAME>` GitHub variable or secret forwards into the store as `<NAME>` on each deploy and wins over the store. A deploy fails before any work when a needed name has no value, and it names each missing name.
- **K-809** The kitshn store encrypts secret values with AES-GCM under a Worker secret. The map shows names and "set" or "missing", never a value.
- **K-810** The workflow file is the same few lines for every app. It needs `permissions: id-token: write` and calls the kitshn action.
- **K-811** Deploy auth: Actions sends its GitHub OIDC token (issuer `https://token.actions.githubusercontent.com`). kitshn accepts a token whose `repository_owner_id` is on its list of owners. It refuses any other token. The list holds user accounts only; GitHub organizations are not on it for now.
- **K-812** A Compose deploy is a job (K-610). Actions sends the checkout, with `.git` and without a stored token, and the `KITSHN_*` params to R2 through the Worker, with its OIDC token. The daemon downloads both with its machine token, only while it runs that job. After the app comes up, the daemon keeps that build and its params on the machine as the last good build (K-718), and replaces it only with the next build that comes up. It builds with Compose at the lowest CPU priority and starts the app with the variables of KitSHn 1 (`KITSHN_SOCKET_DIR`, `KITSHN_DEFAULT_SOCKET`, `KITSHN_ENVIRONMENT`, `KITSHN_DATA_DIR`, `KITSHN_LOG_DIR`, `KITSHN_PARAMS_FILE`, with the params quoted as KitSHn 1 quotes them, so Compose still reads a `$` in a value as a variable), so a KitSHn 1 `compose.yml` works unchanged, within the limits of K-818. The daemon takes the Compose files that Compose finds on its own (`compose.yml` and `compose.override.yml`), or the recipe's `file`, and passes them to Compose by name. KitSHn 1 deploy credentials (`KITSHN_SSH_KEY`, `KITSHN_VPS_HOST`) never reach the app. A machine runs one Compose job per app at a time. When the socket answers, the daemon exposes it under the address name (K-1104), so the tunnel, DNS and Access follow the live site path. The files are deleted from R2 when the job ends, and an R2 rule removes any that remain after a day.
- **K-813** The Actions step asks kitshn for the state of the deploy every few seconds until it ends, and prints the job output and the final address. It fails when the deploy fails. The daemon sends the output at the end of the job, not line by line; revisit when builds get long enough to need live logs.
- **K-814** The deploy ends with a route check: kitshn requests the address and records status and content type, as KitSHn 1 does.
- **K-815** `kitshn try` builds and runs a recipe on the machine of the developer with a temporary socket, as KitSHn 1 `try`. It touches no environment.
- **K-816** kitshn creates a GitHub deployment and its status for each environment, with the address.
- **K-817** Planned ([#60](https://github.com/Yarden-zamir/kitshn/issues/60)). A `push` entry may list several addresses; a `pull_request` entry keeps one (K-901). Each address is the apex or one level below a zone of K-1111, so Universal SSL covers it. The first address under `KITSHN_ZONE` is the main one: it keeps the card address, the expose name (K-1104), the route check (K-814) and the deployment (K-816). Every other address either serves the app, with its own ingress to the same socket, DNS record and Worker route on its own zone, or redirects (301) to another address of the environment with a Single Redirect rule on its zone and no ingress (the API token then needs the redirect rules permission). K-402, K-403 and K-410 hold per address: its Access application comes before its DNS record, and removal runs in reverse. kitshn takes over an existing record only as K-1404 says. The data of a moved app: on the same machine the first deploy takes over the KitSHn 1 data folder (K-1404); on another machine the owner stops the old app, copies the data folder, checks the copy, then deploys and moves the DNS record.
- **K-818** A Compose app gets no more than its own folders, project and network. Each deploy or redeploy unpacks the source into a new folder that no running container mounts. There the daemon first parses each raw Compose file as YAML for `include` and `extends`, before Compose reads them; a file that is not one YAML mapping fails the deploy. `extends` needs an allowance also within one file. Then it reads `docker compose config --format json --no-interpolate`, which names the env and label files without reading them, checks those files, and only then reads the config once more with the params. Every Compose command of a deploy that reads Compose files gets them and the params file by name, so the params and the repo's `.env` add no Compose file; the clean-up after a failed takeover runs by project name in the app's folder, which holds no Compose file. The whole check runs before the KitSHn 1 takeover (K-1404), so a refused deploy leaves KitSHn 1 as it is. The recipe's `file` is a path inside the repo, also after symlinks; a missing file fails the deploy. Only a short list of Compose keys passes on its own (image, build, command, environment, env files, volumes, networks, healthcheck, restart, limits, `scale`, `profiles`, `extra_hosts` and a few more), and only with safe values: build contexts, additional build contexts, the Dockerfile, env and label files stay inside the new source folder after symlinks; bind mounts, secret and config files stay inside the app's source, data, log and sockets folders after symlinks, are no link inside those folders (setting `link:<path>`), and a link whose target is missing fails the deploy; and are not under another writable bind source of the app (setting `nested:<path>`), because Docker follows links at each container start; a built image and its tags are `<project>-<service>` with an optional `:<tag>`, and a container name is `<project>-<service>`; logging is `json-file` or `local`; a service joins networks without aliases or addresses; top-level volumes and networks are plain ones of the app's own project, and a network can be `internal`; no label starts with `com.docker.compose.`; `cache_from` names registry images only. Every other key or value, for example `privileged`, `cap_add`, `pid`, `network_mode`, `ports`, `volumes_from`, `provider`, `post_start`, `security_opt`, `include`, `network:kitshn-edge` or `bind:/var/run/docker.sock`, runs only when the owner names that repo and setting on the allow list of the machine in its panel, for example `Yarden-zamir/dozzle bind:/var/run/docker.sock`; an entry holds for every environment of the repo, previews too. The daemon builds and starts from the checked config itself, not from the repo's files. It builds while the old app still runs. Then it stops every container of the app (by its Compose label, orphans too), checks the bind and file paths once more and runs `up`, so no container of the app can swap a path between that check and `up`. A deploy that fails before `up` starts the old containers again and removes its new folder, so the old app runs on. A failure in `up` or later leaves the app down until a deploy or redeploy comes up. When the app answers, the daemon removes the source folders of earlier deploys. The deploy output names each refused setting. The configs hold the params, so they stay in folders that only the daemon user reads; the daemon keeps only the checked config and params of the last `up`, also of a failed one. A teardown (K-904) runs `down` with them, and also removes every volume with the app's project label. kitshn sends Compose jobs only to daemons that report the capability `compose-guard`. Known limits, to revisit when a second person deploys apps on a machine: apps on one machine share the BuildKit cache; a root container can leave setuid files or device nodes in its own folders on the host; kitshn sets no default CPU or memory limits; Compose gives each service its name as an alias on every network that it joins, so an app with `network:kitshn-edge` can take the traffic of a service of the same name in another app on that network; an image or container name `<project>-<service>` can match the same name of another project when the names have dashes (the project `app-foo-1-prod` with the service `2-prod-web` gives `app-foo-1-prod-2-prod-web`, also the name of the service `web` of the project `app-foo-1-prod-2-prod`), so one app can replace the image that the other built, or one of the two fails to start; the check of nested binds holds only for the app's own config, so a process outside the app that changes links in the app's folders, or a link inside the `subpath` of a named volume, is not checked; the link check reads the path as the Compose file writes it, so an outside path that the owner made a link into the app's folders is checked only at its real target and needs no allowance. Rootless Docker for the kitshn user is the planned next step against these limits.
- **K-819** A repo that kitshn has never deployed waits. Its first deploy step records it by its GitHub `repository_id`, and the step fails with "waits on the kitshn map". The toolbar shows the count of waiting repos. The map panel lists each repo with "Allow" and "Block", and a waiting repo also with "Forget". The panel of each card that the repo deployed shows "Deploys" with the same switch; the card matches by the repo id that kitshn stores with each deploy. "Allow" on a repo that waits after a push starts its workflow again on the first pushed branch through the GitHub App (K-908), and the panel names that branch. Allow is a deploy permission, not an access share, so it works during the pause (K-1504) but starts nothing until Resume. Until a start succeeds, the panel keeps the branch with a "Start" button. After a pull request run, the next run deploys. "Block" cuts a repo off at once, also after a rename or a transfer, because the gate keys on the id: every deploy step checks it, the jobs and Compose deploys of the repo that have not finished fail, kitshn deletes their files in R2, the daemon gets no source of the repo, and agent keys cannot redeploy or build it (K-718). A build whose daemon already downloaded the source can still finish on the machine, and a static upload that already started can finish too; the card stays as it was. A blocked repo still tears down its previews and environments. A repo that finished a deploy before the gate existed counts as allowed; a teardown alone does not count. The gate covers deploys, not jobs: an agent key that manages a machine can still run jobs there (K-718). Only a member with control on the admin card (K-104) blocks or forgets. It allows too, and so does an agent key with "may add apps" (K-718): it sends `{"state": "allowed"}` to `POST kit.<zone>/agent/repos/<repoId>`. A key allows only a waiting repo and not during the pause (K-1504); it never unblocks a blocked repo or changes an allowed one. Its Allow starts the waiting branch as the owner's Allow does, writes a History revision that names the key, and the repo stores the key, which the repo list shows. The owner can still Block. While the key that allowed a repo has no agent circle, for example after the owner removed the key, the repo counts as waiting for every deploy, static, Worker and Compose: the gate refuses, and the repo list shows it as waiting with "allowed by <name>, key removed". This lasts until the owner takes it over, blocks it, or gives the key an agent circle again. A teardown of such a repo always runs. "Take over" on such a repo is the owner's Allow: it clears the key, and the repo then follows the rules of an owner Allow. Block clears the key too. `GET kit.<zone>/agent/state` lists the waiting repos with their ids for a key with "may add apps". A key never writes allow entries: they are the owner's (K-818), and a new repo has none, so the daemon refuses every risky Compose setting of a repo that a key allowed. Known limit: the allow list keys on the repo name, so a new repo under a freed name, also one that an agent created, gets the entries of the old repo. Revisit this when the allow list keys on the repo id. Known limit: a Compose job that waits in the queue is not checked again when kitshn sends it to the machine. Known limit: after Take over, the recipe's `startsIn` places the new cards of the repo again (K-807). A Compose app of such a repo goes only to a machine where the key may run jobs (K-718). kitshn checks this at the plan and again at the start of the job; without such a machine, the step fails and says why. Static and Worker sites need no machine. A new card of such a repo starts in the first agent circle of the key at the level `control`, not in `startsIn` (K-807); without one, or during the pause, it waits in the tray. This bends K-002: a new repo needs one click by the owner before its first deploy, because with OIDC (K-811) any repo of a trusted owner, also one that an agent created, could otherwise deploy code onto a machine.

## 9. Previews

- **K-902** A preview of a Compose app runs on the machine of its app. It gets a tunnel route to its socket and a DNS record.
- **K-903** A preview of a static site or Worker app is its own Worker script with a custom domain. The free plan allows 100 Worker scripts per account; kitshn refuses a new preview at 90 and names the open previews.
- **K-904** With the GitHub App (K-908), a closed pull request removes its preview at once: containers, images, volumes, socket, route, DNS record, Access application and card. Without the App, the workflow does it on the `closed` event, as KitSHn 1.
- **K-905** Planned: today a closed preview loses all its data. A preview keeps what the recipe lists in `keep` (logs, data folders), as KitSHn 1. "Prune" in the card panel removes what is kept.
- **K-906** Preview limits work as KitSHn 1: `limits: { cpus, memory }` caps all previews of an app together. Production is never limited.
- **K-907** A preview starts in its `startsIn` circle, by default "Owner".
- **K-908** The kitshn GitHub App adds: preview teardown on close (K-904), deployment statuses (K-816) without a workflow token, builds that agent keys start (K-718, with the permission "Actions: write"), "Allow" that starts the refused push again (K-819), repo cards before the first deploy, and "New app" from the map, which creates a repo from a template. The owner creates the App after the spec is approved.

## 10. Artifacts library

- **K-1001** Every HTML page from T3 threads on every machine goes into one library in R2. The provider sends each new `html_render` page with `publishPage` (K-708), with its thread title, machine and time.
- **K-1002** A new page is private: it sits in the tray (K-509), unless the owner drops it on the map (K-1101).
- **K-1003** The Worker serves a page at `pages.<zone>/<id>`, with the sandbox of the T3 render route (no same-origin scripts). Only the kitshn admin host may frame a page or a file (`frame-ancestors`), for the previews of K-520. The id is random, 16 characters or more.
- **K-1004** The Worker checks shares for each page request (K-404). A page in "Everyone" opens with no login. Other pages need a login through an Access application on `pages.<zone>/login`, which sends the visitor back. A second application on `pages.<zone>/login/passkey` adds the passkey check, for circles with "needs passkey" (K-103). Files use the same two paths on `files.<zone>`. Checked on 2026-10-27: a service token on `/login` gets the `CF_Authorization` cookie with `Path=/`, and a plain login cookie does not pass `/login/passkey`. Both applications write that one cookie, and Cloudflare advises against relying on it. So each login path checks the token that Access sends with it (`Cf-Access-Jwt-Assertion`) against its own application, and the Worker keeps it in its own cookie on `/` (`__Host-kitshn-login-token`, `__Host-kitshn-passkey-token`) for as long as the token lives. A cookie name never sets the level: the audience of the token does. A logout at the Access logout URL does not end these cookies; "Sign out everywhere" (K-110) and the loop guard do. A login path whose token does not prove that step answers with the reason at once. Each login path marks its return in a 60-second cookie on the item's path; when the item still cannot use the login after that step, the Worker answers with the reason and what it saw in each token instead of a second round, so a login never loops. Only people who can open an item may log in, so a stranger cannot take a Zero Trust seat (K-111). The login applications get their own copies of the people rules of every circle with an active page, file or admin share; Access applications of cards keep the people policy. `/login` gets a copy without the passkey check for each such circle, because that step comes first. `/login/passkey` gets a copy with the passkey check for each such circle with "needs passkey". A circle with "everyone" adds nothing, because its items open without a login. An "all must match" circle adds its people rules as they are, because its require rules let in only the circle. Ended shares and circles add nothing, and during a pause (K-1504) only the Owner circle stays. The `/login` applications also always get the machines policy of the bootstrap; the Worker removes every other policy. It then deletes the policies "kitshn any login" and "kitshn any login (passkey)" of older bootstraps when no application uses them. A policy goes on a login application only after Cloudflare holds its current body, so a new passkey check is never skipped. While the login applications hold a copy, the Access sync neither changes nor deletes it until the login step lets go of it; after a login step that failed part way, both the earlier and the new copies count as held. So a failing login step never holds back a policy of a card (K-409). The first run after a deploy fails closed: until the next alarm adds the circle policies, no person can log in to pages and files. When someone deletes a login policy in the dashboard, its old id stays until the daily compare, so login updates can fail until then. A failed write shows as an Access warning on the map and waits for the daily retry; the daily compare (K-408) repairs the applications. Milestone 3 tests it.
- **K-1005** The Library view lists all pages with a search by title, thread and machine, and a preview. It reads the index in the Durable Object, not R2.
- **K-1006** Deleting a thread does not delete its library page. "Delete" in the library removes the page from R2 and the map.
- **K-1007** An MCP App page is not shared, because its buttons need its live MCP server. The library keeps it private and says why.
- **K-1008** An import adds all past pages of each machine once. Each imported page is private, as a new page (K-1002). Work pages (QCDI, Upsolver, SDE) are no exception. On 2026-10-27 there are 46 pages, about 14 MB: 41 on the Mac, 5 on the VPS, 0 on the Oracle VPS. Pages on Windows are not counted, and wait for the Windows daemon (K-601). New pages arrive at about 20 per week.

## 11. Files and sites

- **K-1101** "Upload" on the map, and `kitshn_publish` for agents, put a file into R2 and a card into the tray. A file is at most 100 MB. A file dropped from the computer onto the map lands where it was dropped instead, in one revision, so it gets the shares of the circles there at once; an `.html` file becomes a page. A drop into a public circle asks first (K-210), and one Undo takes back the whole drop (K-503).
- **K-1102** The Worker serves files at `files.<zone>/<id>/<name>` with the checks of K-1004.
- **K-1103** Public sites (for example tick3d and the resume) are static sites (K-805) in the Everyone circle.
- **K-1104** A live site is a local server of a machine, shared through the tunnel of the machine. `kitshn expose <socket or port> --name <name>` or `kitshn_expose` adds it, and `kitshn unexpose <name>` removes it. kitshn makes its card, its DNS record and its ingress only when nothing else uses the address, and its DNS record and ingress only after its Access application exists. `kitshn_expose` is the agent tool of milestone 5 (K-714). Its address is `<name>.<zone>`. It is live only: when the machine is off, the site is off. kitshn keeps no copy.
- **K-1105** A live site of a dev server gets the `Host` header `localhost` toward its origin, because Vite and similar servers refuse other hosts.
- **K-1106** When the origin of a live site or of a Compose app is down, visitors who pass Access get the kitshn offline page:
  - It uses the kitshn look (K-517), a short playful message, the site name, the machine name, the time the site was last seen, and "It comes back when <machine> is on."
  - It has one button, "Knock again", which loads the address again. It has no continuous animation and no automatic reload.
  - The response is status 503 with `Retry-After: 60` and `Cache-Control: no-store`.
  - The Worker serves it from its own static assets, with no call to the machine.
- **K-1107** kitshn detects a down origin in two ways, and acts on either:
  - The machine is off: its daemon socket closes, or misses pings for 30 seconds.
  - The machine is on, but the local server is off: the daemon tries the socket or port of each exposed site every 10 seconds, on the machine only, and reports a change.
- **K-1108** While an origin is down, kitshn adds a Worker route for the site address to the kitshn Worker. When the origin is back, it removes the route. So visits to a healthy site never run the Worker and cost no Worker request. Custom error rules would do this with no Worker, but the free plan has none ([Custom Errors](https://developers.cloudflare.com/rules/custom-errors/)).
- **K-1109** While the route exists, the Worker first passes the request to the origin. It shows the offline page only when the answer is status 502 or 530, or a Cloudflare 1033 error. So a site that comes back before kitshn removes the route works at once. Checked on 2026-10-27: the offline route was still on the hostname, and the restarted origin answered 200 through the Worker. So the fetch did not run the Worker again.
- **K-1110** The Worker reads the site name and the last seen time from the Durable Object, and keeps them for 60 seconds in the Cache API.
- **K-1111** Domains: kitshn publishes only on zones that the owner adds to it. Each address must be in one of them.

## 12. Bootstrap

- **K-1201** One command sets up kitshn on a new Cloudflare account: `curl -fsSL https://kit.yarden-zamir.com/install | sh`, with the Cloudflare API token in `CLOUDFLARE_API_TOKEN`. The `/install` path needs no login.
- **K-1202** The owner makes the token by hand through a link with the permissions filled in. The script names each missing permission and the link.

## 15. History and safety

- **K-1501** Every change makes one revision with the time, the actor (owner device, agent with machine and thread, or kitshn for an expiry) and a summary.
- **K-1502** "Undo" on a revision makes a new revision that reverses it. Undo runs the guard of K-105.
- **K-1503** Revisions older than 90 days and beyond the newest 5,000 are deleted by the daily alarm.
- **K-1504** "Emergency pause" is a big red button, always in the toolbar and in the command palette. One press opens a short confirm that names what stops; its button then pauses. The confirm has one option, "Also close public sites", which is off. Without it the pause keeps the shares of public circles (Everyone, "any must match") on sites, pages and files, so public sites, apps and pages stay up, as in the old portal; a public share of a machine or a repo still closes. With it the pause is a lockdown. The pause moves no card, but stops: every share except the admin share of the Owner circle for its people and, unless it is a lockdown, the shares of public circles, so other sites, Compose apps, live sites, pages and files close; every share of devices, agent keys and machines, so agent keys stop moving, deploying and running jobs (K-718), and the jobs that devices and agent keys queued fail; new deploys from GitHub, which wait until Resume (a preview teardown still runs, and a deploy that already runs finishes behind closed doors, with its card in the tray); and "stop all agents" to every provider that has the command (providers arrive in milestone 5, so today no running T3 agent stops). Pages and files close at once; Access applications close through the alarm queue of K-406, so many applications take a few alarm runs. Machines stay connected and their apps keep running behind closed doors. The owner keeps the admin and the machine commands they had (MM-711), and while paused any change that would raise access is refused; lowering access still works. Every view shows a hazard frame and a red banner with the kind of pause (public sites open, or lockdown), who paused and when (stored with the pause), and "Resume". A pause can become a lockdown with an edit, which keeps who paused first; the history names the kind of each step. Only Resume ends a pause or opens public sites again after a lockdown. A public site, Compose app or live site on a machine stays public in a pause that is not a lockdown. Resume needs a fresh passkey: the owner passes the passkey check of the `kit.<zone>/api/fresh` application (its own cookie path, a session and an MFA session of ten minutes), confirms once more, and only that path ends the pause; the people who can Resume are the owner emails of the bootstrap that are also in the Owner circle; an edit or an undo never does. VERIFY: that the MFA session of ten minutes asks for the passkey again after the 24-hour login of the admin; milestone 6 tests it. Resume returns the shares. Dropped from the machine map: the flip-up cover, sounds and counts popover of MM-708 (the confirm replaces them), the cut wires of MM-717 (circles have no wires), and the T3 lock of MM-718 until K-1618.

## 16. Machine map features

This section lists every feature of the machine map portal (`apps/machine-map/SPEC.md` in the T3 Code fork, `MM-` numbers) that the sections above do not cover yet. Each one is planned for a milestone of [docs/migration.md](docs/migration.md) or dropped with its reason, so nothing is lost at the cutover (K-1401).

- **K-1601** Phone app invites (MM-911 to MM-915, MM-1122, MM-720). "Add phone" makes a device member (K-106) and an invite: a QR code and a link with a one-time code of 128 bits that expires after 15 minutes, with the attempt limits of join codes (K-602). The app exchanges the code once and gets its service token only in that answer; kitshn stores the client id, never the secret. The invite dialog links "Add with Obtainium" for the fork Android app (prereleases, APK filter `android\.apk$`). The app reads its machines from `kit.<zone>/device/machines`, which has its own Access application for service tokens (K-1204) and answers with the `t3.app` cards that the token opens and their addresses, at start and on "Refresh machines". Only the owner makes or cancels an invite, and an undo never adds, changes or removes a device token. Milestone 6.
- **K-1602** The Clients view (MM-901 to MM-903) lists the Access sessions of kitshn's applications and the sessions that providers report as lists (K-1625), one row per subject and label. "Sign out" on a row sends the provider command "revoke client". "Sign out everywhere" (K-110) also ends those sessions, and an offline machine gets it from its queue. Milestone 6.
- **K-1603** Dropped: browser keys, their approval flow and `clientAccess` (MM-904 to MM-910, MM-916 to MM-918, MM-920 to MM-922, MM-1207 to MM-1209), because a passkey circle and device tokens replace them (K-108). Kept from MM-919: a machine joins or leaves kitshn only from its local desktop app, `kitshn join` on the machine or the installer; `kitshn_join` and remote T3 clients refuse it, because leaving would turn off the grants that the provider enforces.
- **K-1604** Health thresholds and alerts (MM-1504, MM-1505, MM-1509, MM-1511). Each machine has thresholds with the defaults of MM-1504, which the owner edits in the machine panel; an empty field turns a check off, and a threshold edit is no revision. The daemon checks its own samples, so samples cause no Durable Object writes (K-1302), and reports only the start and the end of an alert. A machine card shows one sticker per active alert (HOT, FULL, DISK, SWAP, DOWN, LOW); kitshn starts DOWN itself after the offline threshold. Alert starts and ends show in History as events, not as revisions, and kitshn keeps them 30 days, at most 500. Milestone 6.
- **K-1605** Resource history (MM-1501, MM-1503, MM-1506 to MM-1510). The machine panel shows charts of CPU, CPU pressure, memory, disk, battery and agent processes for the last hour, day and 30 days, from the history that the daemon keeps (K-606), and the top processes now. An offline machine shows its last sample and says that its history needs it online. The Health view compares the machines and lists the alerts. `kitshn_resources` returns the same data to agents. Charts change only when a sample arrives. Milestone 6.
- **K-1606** Installed app and Web Push (MM-1801 to MM-1809). The map is an installable web app with a manifest, maskable icons and the shortcuts Emergency pause, Inbox, Health, Queue and Tasks. Its service worker caches only the files of the current build and an offline page, never state. kitshn sends Web Push with the Web Crypto API and a VAPID key that the bootstrap stores as a Worker secret (K-1204), one subscription per browser, when an alert starts, a proposal waits, and on the pause. "Sign out everywhere" deletes every subscription. The app badge counts proposals and active alerts. Milestone 6.
- **K-1607** The Inbox (MM-802 to MM-804). Agent changes that become proposals (K-715) wait in the Inbox view. The owner approves or rejects each one; a proposal expires after 24 hours. Each proposal names its reason ("own access" or "owner only") and its agent, machine and thread. An approve runs the guard of K-105 like any change. Milestone 5, because `kitshn_share` and `kitshn_circle` make the first proposals.
- **K-1608** The queue of offline machines (MM-601 to MM-608), beyond jobs (K-613). The provider desired state (K-709, K-717) and the grant tables (K-706) of an offline machine wait for it: its card shows "queued" with a count, and the machine reports the last revision that it applied. On connection it applies the current state, not each queued revision. On start it applies its last saved state before it accepts connections. "When online and idle" waits until no provider of the machine reports `busy` (K-1625). The Queue view (K-519) lists every queued change and job, oldest first, with "Cancel" for jobs. Milestone 5.
- **K-1609** Cross-machine calls (MM-1901 to MM-1907, MM-1909 to MM-1921, MM-1923, and the exec rules of MM-1908). A link from A to B needs two shares: B's `t3.app` card with a circle that holds A at `view` or higher, so Access lets A reach B's T3 address (K-402, no exception), and B's `t3.agents` card with such a circle. A `t3.agents` share without a `t3.app` share gives nothing. The level of A on B's `t3.app` card sets the link access and the fence of MM-302. `use` makes B a linked environment of A; `exec` adds `kitshn_exec`, only at the `t3.app` level `use` or `control`, refused below full-access, for at most 90 seconds and 50,000 bytes per stream. The daemon of A makes the connection with its machine token for the provider (K-711). The rules of the T3 side stay: the source thread's limits travel with each call and the narrower limit wins, a target that cannot enforce them is refused, threads, attachments, the `@` menu, `delegate_task`, watches and terminal threads work across machines as MM-1905 to MM-1923 say, B trusts the origins of its linked peers (MM-1311), and the emergency pause makes every link unreachable. The card panel lists what agents on A can do on B (MM-1915). `t3 machine exec` streams a run as MM-1919 says. Copying secrets (MM-1917) stays out until a service enforces it. The provider trusts the Access JWT header only because T3 listens on loopback behind the tunnel (MM-1206). Milestone 5 builds the grants and links; milestone 6 turns them on.
- **K-1610** Audit of cross-machine work (MM-1908, MM-1922). The source machine reports each `kitshn_exec` run and each forwarded T3 tool call to kitshn: the source and the target machine, the calling thread, the command or the tool name, the working directory, the outcome, the exit code and the time, never the arguments or the output. History shows them as events, not revisions, so they have no Undo, and `kitshn_read` lists the newest 50. kitshn keeps them 30 days, at most 2,000; the budget table counts them (K-1302). Milestone 5.
- **K-1611** T3 Code panels (MM-203, MM-1701, MM-1921). T3 Settings > Machines joins with a code and leaves kitshn on the local desktop app (K-1603), and shows the connection state. The Machines panel in T3 Code shows the map from `kitshn_read`, read only, with a link to the map. Settings > Connections shows the links from `t3.agents` shares read only, with "Change access on the map". When a share to or from the machine lowers or ends, T3 shows an access change notice there and in the threads that used the link. Milestone 6.
