# KitSHn 2 spec

KitSHn 2 runs your apps, sites, pages, files and machines on Cloudflare, and decides who may open each one. It puts everything on one map. Circles on the map say who. A card inside a circle is shared with that circle.

The repo is named "KitSHn 2". "kit" is the short name of the project. Code, packages and the MCP tools use `kitshn`. The CLI is `kitshn`, with `kit` as a short alias. The admin and the map live at `kit.yarden-zamir.com` (K-1208).

Requirements have stable numbers with the prefix `K-`. Do not renumber them. Mark a removed requirement "Removed" and keep its number. `VERIFY:` marks a Cloudflare fact that the docs do not confirm; the first milestone that needs it tests it.

The architecture, the request paths and the budget are in [docs/architecture.md](docs/architecture.md). The order of work is in [docs/migration.md](docs/migration.md).

## Core rules

- **K-001** The app and what it needs to deploy live in its repo. The places (machines, the Cloudflare account, domains, who may open what) live in kitshn, never in the repo.
- **K-002** "Create a repo, push, and it deploys" stays true. A new app repo needs a recipe and a workflow file, and nothing else: no per-repo secret, no setup step in kitshn. The one exception is the first deploy of a repo, which waits for one click by the owner or by an agent key that may add apps (K-819).
- **K-003** kitshn runs on Cloudflare only. Its logic and state run in one Worker with one Durable Object. Machines do only machine work: tunnels, local sites, Compose deploys, commands and builds.
- **K-004** kitshn fits the Cloudflare free plan for the setup of K-1301. A paid plan only raises limits; no feature needs it.
- **K-005** kitshn knows nothing about T3 Code. T3 Code and other programs add their own resource kinds through the local interface of section 7.
- **K-006** Every unexpected state fails closed: a request that kitshn cannot decide gets no access, and the error says why.

## Terms

- **Owner:** the person who installed kitshn. The owner is the first member of the "Owner" circle.
- **Circle:** a named group of who: people (emails), email domains, devices, networks (IP ranges), machines, and the flag "needs passkey". A circle has a default level.
- **Resource:** something that kitshn can share: a machine, a site, a page, a file, an app, a thread. Each resource kind names its levels.
- **Card:** a resource on the map.
- **Share:** a card inside a circle. It gives the members of the circle the circle's default level on that resource, or the level of an override.
- **Level:** what a share allows. Each resource kind names its own ordered levels, for example `view`, `use`, `control`.
- **Daemon:** the `kitshn` program on a machine.
- **Provider:** a program on a machine that adds resource kinds through the daemon, for example T3 Code.
- **Recipe:** `kitshn.config.ts` in an app repo.
- **Environment:** one deployed copy of an app, for example `prod` or `pr-12`.
- **Job:** one piece of machine work, for example a Compose deploy.

## 1. Identity and login

- **K-101** Cloudflare Access does every login. kitshn has no login code and no password store.
- **K-102** People log in with the Access One-time PIN (an email code). GitHub is a second login method next to the email code. The passkey check of K-103 applies after either login method.
- **K-103** A circle with "needs passkey" asks for a passkey or a security key after the login, through Access independent MFA. [Independent MFA](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/independent-mfa/) supports biometrics (Touch ID, Face ID, Windows Hello) and security keys, per application and per policy.
- **K-104** kitshn administration is a resource of kind `kitshn.admin` with the level `control`. Its card sits in the "Owner" circle. The Owner circle has "needs passkey" on.
- **K-105** kitshn refuses every change that leaves the admin resource without a share to a circle that has at least one person and "needs passkey". This guard runs on every write: a drag, a circle edit, an undo, an agent tool and the pause (K-1504). It also refuses a share of the admin resource with a circle that has "everyone", because that circle compiles to an Access Bypass policy.
- **K-106** A device proves itself with an Access service token: one token per device, for example "Mac desktop app" or "Yarden's phone". A device is a circle member like a person.
- **K-107** A machine proves itself to Access with its own service token (K-602), and to kitshn also with its own key pair (K-1704). A machine is a circle member too, so a share can give one machine access to another resource.
- **K-108** Browser approvals of the machine map (browser keys, the Clients approval flow) do not exist in kitshn. A passkey or a device token replaces them.
- **K-109** Access sessions of the admin resource last 24 hours. Sessions of other resources last 30 days unless a circle sets a shorter time.
- **K-110** "Sign out everywhere" ends every Access session of every application that kitshn made, through the Cloudflare API. It does not end sessions of other applications (K-408). The Worker also refuses page and file logins from before the sign-out (K-1004). It runs at once, without a confirm; its label and tooltip say that every session ends. History records the start, before any Cloudflare call, and then the outcome: how many applications ended their sessions, and which failed. While an application is left (a failed call, the call limit of one request, or a failed list of applications), the Access warnings name it with "Retry sign-out", which is also in the command palette. A retry revokes only the applications left that kitshn still has, or starts over after a failed list; an application that Cloudflare no longer has counts as ended. History records each retry's outcome, and the warning goes when every session ended. One sign-out or retry runs at a time.
- **K-111** Zero Trust Free counts one seat per person who logs in, up to 50. kitshn turns on seat expiration in Zero Trust admin controls, set to 1 month, so guests who stop coming free their seat. [Seat management](https://developers.cloudflare.com/cloudflare-one/team-and-resources/users/seat-management/) runs the expiry once a day.
- **K-112** The admin view shows the seats in use, with a warning at 40. The view can also remove a seat. Checked on 2026-10-27: `GET /accounts/{id}/access/users` lists each user with `seat_uid` and `access_seat`. VERIFY: the [seat API](https://developers.cloudflare.com/api/resources/zero_trust/subresources/seats/methods/edit/) `PATCH /accounts/{id}/access/seats` turns a seat off. Milestone 2 tests it with the Seats view.
- **K-113** Every person in a circle with "needs passkey" can open the App Launcher, because Access enrolls a passkey there (`https://<team>/AddMfaDevice`). kitshn keeps one reusable policy "kitshn passkey enrollment" on the App Launcher application, made from the emails and domains of the passkey circles with "any" match that have not ended; during a pause (K-1504), only of the Owner circle. A circle with "all must match" is left out, because its rules joined with "or" would let in more people than the circle does. A failed write of the App Launcher waits for the daily retry. It adds that policy next to the existing policies of the App Launcher and never changes or removes another policy there. The daily compare (K-408) repairs it. The circle editor shows the enrollment address while "needs passkey" is on.

## 2. Circles and shares

- **K-201** A circle has a name, a colour, a default level, members, a match mode (K-203), an optional end date, and the flag "needs passkey".
- **K-202** Member kinds: an email, an email domain, an IP range, a device token, a machine, and "everyone". "Everyone" means anyone who can reach the address, with no login.
- **K-203** A circle has one of two match modes:
  - "Any" (the default): the visitor matches at least one member. In Access, the members are include rules.
  - "All must match": the visitor matches every member, for example the domain `qlik.com` and the IP range of the Qlik network. In Access, the members are require rules. This replaces the "required IP ranges" of the machine map Guests view.

  With "needs passkey", the visitor must also pass a passkey check in both modes.
- **K-204** A card is shared with every circle that it sits inside. Circles overlap freely, and there is no limit on their number.
- **K-205** A share uses the default level of its circle. One card can override the level for one circle. The override shows as a chip on the card.
- **K-206** A level that the resource kind does not have becomes the highest level of that kind that is lower. A circle with the default `control` thus gives a file `view`.
- **K-207** When several circles match a visitor, the visitor gets the highest level of those shares.
- **K-208** A card outside every circle is private. Only the admin (K-104) can see it in the map.
- **K-209** A share can have an end date. At the end date, kitshn moves the card out of that circle as a new revision, and the history names the expiry.
- **K-210** A circle with "everyone" asks for confirmation the first time that a card enters it: "This makes <name> public."
- **K-211** The Owner circle and the Everyone circle exist from the start. The owner can rename them, and cannot delete the Owner circle. A delete of another circle runs at once, without a confirm; the toast and History undo it (K-1502).

## 3. Resources

- **K-301** Built-in resource kinds and their levels:

  | Kind | Levels | What it is |
  | --- | --- | --- |
  | `kitshn.admin` | control | kitshn administration (K-104) |
  | `machine` | view, use, control | a machine with a daemon (section 6) |
  | `site.static` | view | a static site on Workers static assets |
  | `site.worker` | view | a Worker app |
  | `site.compose` | view | a Compose app on a machine |
  | `site.live` | view | a local site of a machine, through its tunnel (K-1104) |
  | `page` | view | an HTML page in the library (section 10) |
  | `file` | view | a file in R2 |
  | `repo` | view | a repo that has a recipe; its environments are its children |

- **K-302** A provider adds kinds through the daemon (K-704). Each kind has an id with the provider prefix (for example `t3.thread`), its levels, and how it is enforced (K-405).
- **K-303** An environment of an app is its own resource and its own card, for example "riffle" and "riffle pr-41". New environments start in the circle that the recipe names (K-807).
- **K-304** Each resource has an id, a kind, a name, an owner machine when it has one, its addresses, and its status. The status is one of: running, stopped, deploying, failed, offline, unknown.

## 4. Enforcement

- **K-401** kitshn compiles shares into Cloudflare Access wherever Access can check them, so a check costs no Worker request.
- **K-402** Each circle becomes reusable Access policies: one for its people (Allow, with the passkey check), and one for its devices and networks (Service Auth), because Access lets service tokens and logins without a person in only through Service Auth. A resource with an address becomes one self-hosted Access application whose policies are the circles that hold it. Checked on 2026-10-27: the API attaches one reusable policy to two applications, and the policy reports `app_count` 2. The account limits are 500 applications and 500 reusable policies ([account limits](https://developers.cloudflare.com/cloudflare-one/account-limits/)).
- **K-403** A resource inside "Everyone" gets a Bypass policy, or no Access application.
- **K-404** The Worker checks shares itself for what it serves: pages and files (section 10 and 11). It reads the Access JWT and the visitor IP; its only cookies of its own hold the Access tokens of the login steps and the return mark of a login step (K-1004).
- **K-405** A provider enforces levels inside its own program. kitshn gives it a grant table for each of its resources (K-706). Access still guards the address: it lets in every circle with a level above none.
- **K-406** kitshn writes Access changes in a Durable Object alarm queue. One alarm run makes at most 40 Cloudflare API calls and sets the next alarm when work remains. The free plan allows 50 subrequests per request ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)).
- **K-407** The map shows a change at once. Each card shows "applying" until Cloudflare has the change, and "failed" with the reason if Cloudflare refuses it.
- **K-408** A daily alarm compares Access with the shares and repairs differences that kitshn made. It never changes an Access application or policy that kitshn did not make, and it names such an application when it covers a kitshn address. The one exception is the login applications of pages and files: kitshn removes every policy there except its own and the machines policy (K-1004).
- **K-409** A lower level takes effect at once: kitshn revokes the Access sessions of the affected application, and providers end the sessions of members that lost a level.
- **K-410** Removal order: kitshn never deletes an Access application while a route can still reach its address: tunnel ingress, a DNS record, a Worker route or a custom domain. It takes the route off and confirms it, then the DNS record, and deletes the Access application last. A failed step stops the sequence and retries after five minutes.

## 5. Map UX

The map is the main view. These requirements improve the demo of 2026-10-26.

- **K-501** The map shows every card and every circle. The "Show" menu of the toolbar has a toggle for each kind, which hides that kind. Hidden kinds still count for their circles.
- **K-502** A drag of a card, or of a selection, into or out of a circle shows a preview before the drop: each circle edge lights up, and a label says what changes, for example "+ Qlik · view" or "− Her". The drop applies it.
- **K-503** After each drop that changes a share, a toast names the change and has Undo for 10 seconds. Undo is also in the history (K-1502).
- **K-504** A drag of a circle by its head moves its cards with it. ⌘ and a drag on macOS and iOS, or Ctrl and a drag on other systems, moves the circle alone. The tooltip of the head and the hint line name the key. The preview of K-502 then names every card that gains or loses the circle.
- **K-505** A resize of a circle shows the same preview as K-504 before the release.
- **K-506** A circle shows its members as chips on its edge, at most 4. A "+N" chip opens the full list. The circle head sits on the top of the edge. When a card covers that spot, the head slides along the edge to the first free spot, at most 55° to each side; when no spot is free, the head stays at the top. Heads draw above cards, so a card never hides a head or its level sticker. Known limit: two heads can still overlap each other. Revisit this when circles often touch at their tops.
- **K-507** A card shows a dot for each circle that holds it, and a chip for each override (K-205). A hover on a dot names the circle and the level.
- **K-508** Cards stack by group: the environments of one app, the pages of one thread, the files of one upload. A stack shows the top card and a count. A click spreads it in a row. A drag of a stack moves all its cards.
- **K-509** New cards arrive in a tray at the edge of the map, outside every circle, so they start private (K-208). Cards that a recipe places (K-807) and files dropped on the map (K-1101) skip the tray. The tray lists every such card, newest first, with a filter, and scrolls on its own. A card dragged from the tray, or several picked with Shift, lands where it is dropped, in exactly the circles there (K-204, K-210).
- **K-510** Multiselect: a box drag on empty space, Shift and a click, and "Select all of this kind" in the context menu. A selection moves as one.
- **K-511** The command palette (Cmd+K or Ctrl+K) finds every card, circle and action. "Share <card> with <circle>" works without a drag, also on a phone.
- **K-512** The card panel shows who can open the card: each circle, its members, the level, and the address. It has "Copy address" and "Open".
- **K-513** Zoomed out under 40%, cards become dots and each circle shows its counts by kind. The map never animates continuously, and a change plays at most one short transition.
- **K-514** Pan, zoom, fit and auto layout work as in the machine map (MM-1111, MM-1114 to MM-1121). Each device keeps its own view in local storage. The map fits on load when the device has no saved view, and when the panel (K-519) opens or closes while the owner has not panned or zoomed since the load. A fit shows every circle with its heads and every card whole in the free area, left of an open panel, right of the tray, below the toolbar and above the hint line, and zooms out as far as that needs, down to 0.15. On a wide screen a saved view zooms out no further than 0.85, so card names stay readable; the wheel zooms out further. Fit, and the pan of "Show details" and of a History row (K-1508), keep circle heads and cards clear of the toolbar, the tray and an open panel (K-519).
- **K-515** A card of an offline machine, or of an app on it, shows the "offline" sticker and the time since it was last seen.
- **K-516** The map works on a phone: a long press opens the context menu (K-523) and starts a drag, and a move after it closes the menu. The panel (K-519) is a bottom sheet over the lower half of the screen, and its full view takes the whole screen.
- **K-517** The map uses the tick3d look in light and dark mode (the `neo-brutalism` skill): lilac dotted canvas, ink borders, hard shadows, tilted stickers, Bricolage Grotesque. It uses the standard components of the skill and no native browser UI: every icon button, control, option, sticker and short label has a tooltip. Needed information is never only in a tooltip.
- **K-518** Map state (places, circles, members, shares, stacks) lives in the kitshn database, never in Git (K-001).
- **K-519** Views next to the map: History (with presets, K-716), Queue, Inbox (K-1607), Seats, usage, Machines (a table of status), Health (alerts and charts, K-1604, K-1605), Settings (K-1613), Tasks (K-1614), Clients (K-1602), Library (section 10). Each view and each selected item has its own link; `#map/<card id>` selects the card. Known limit: a selection on the map does not change the link. Revisit this when links to selections get shared often. History, Library, Machines and the details (the selected card, stack or circle, or the map with its circles and repos) open in one panel that floats over the right side of the map, from the toolbar tabs; a selection on the map shows its details there. The panel has a header with its title, "Enlarge", and Close. "Enlarge" opens the full view of the same content: the tab view of History, Library and Machines, or the details over the whole map; "To the map" goes back. A panel that opens puts the focus on its heading, and its header stays at the top while it scrolls. Escape outside a text field and a dialog first clears a selection, then closes the panel, and the focus goes back to the control that opened it; in the History search, Escape first clears the search. After Close, the Map tab shows as not pressed, and a click on it opens the panel again. The map keeps its full width under the panel. Beside the panel, the toolbar and the hint line end at the panel edge, and the hint wraps.
- **K-520** "Previews" shows a live view of up to four site and page cards near the centre of the map, from zoom 80%. Each is a lazy, sandboxed frame that takes no clicks until "Interact". A site behind Access shows only when the browser has its Access session already, because the Access login refuses to load in a frame; the card offers "Open site" to log in.
- **K-521** The owner can stack cards: drop a card on another card, or select several cards and choose "Stack". A stack has a name and holds two or more cards; a card is in one stack at most. Its cards sit on one point, so the stack moves as one and every card of it gets the same circles; moving one card moves its stack. A level override (K-205) and an end date (K-209) stay per card; when a stacked card's share ends, the card leaves its stack. Closed, a stack is one card that lists its cards from top to bottom; a click opens it as a column of cards. Stacks by group (K-508), such as the previews of an app, stay as they are.
- **K-522** The stack panel renames the stack, pulls one card out (it lands next to the stack, in the same circles, so no share changes), and "Unstack" spreads all cards in the same circles. Each of these, and a drop that makes or grows a stack, is one revision with Undo (K-1502); a stack that enters a public circle asks first (K-210). A drop from the tray never stacks, and a stack by group dropped on a card joins that card's stack. While a drag is over a card, the card is outlined and the label says "Stack with" it.
- **K-523** Cards, stacks, circles and the empty map have a context menu. A right-click opens it, and so do a long press on touch (K-516), Ctrl and a click on macOS, the menu key, and a "⋯" button on each card, stack and circle head and on each card in the tray, which the keyboard reaches. Zoomed out (K-513), a card is a dot without "⋯"; a right-click and the menu key on the focused dot open its menu. The menu holds the same actions as the toolbar, the panel and the command palette, from one list per item, so the palette (K-511) has every menu action. A card has: Show details, Open and Copy address, Place on the map (a card in the tray), Share with and Unshare from a circle, its level in each circle for a kind with more than one level (K-205), Select all of its kind (K-510), Leave its stack or Add to a stack, Move to tray, and for a machine Restart daemon, Update daemon (K-612) and Remove machine (K-615), and Remove app (K-909) for a deployed app, and Undo last change to this card (K-1507; in the palette only for the selected card). A stack has Show details, Rename, Share with, Unshare from, Pull out and Unstack (K-522). A circle has Edit, Rename, Add a member, Undo last change to this circle (K-1507; in the palette only for the selected circle) and Delete circle (K-211). The empty map has New circle and Upload a page or a file at the clicked point, and Add a site, Add a machine and Fit; a new site and a new machine start in the tray. An action that the rules refuse (K-105, K-521, K-1504), or a share that no spot on the map fits, shows disabled with the reason as its tooltip, and the palette leaves it out. In a sub-list, Back and Escape return to the item it came from. A dangerous action has no confirm: it runs at once and shows Undo, or, when it cannot be undone, its label names what goes. In the palette, Enter runs a dangerous entry only when it is the only match or the owner picked it with the arrows or a click.
- **K-524** A card shows the icon of its item before its name, in a small tile with an ink border, in light and dark mode. The tile has a tooltip that says where the icon comes from. A static site shows its site icon (K-1112). A repo whose name has the form `owner/name` shows the GitHub avatar of the owner (`https://github.com/<owner>.png`), which needs no GitHub App; the repo list of the map panel (K-819) shows the same avatar. Today only the demo makes `repo` cards, so the avatar shows in the repo list; the planned repo cards get it when they come. A machine shows its system (macOS, Linux or Windows) from the `os` of the last daemon status (K-605), also while it is offline. Without such an icon, or when the image does not load, the tile shows the icon of the kind. The card, the tray, the details, the stack lists and the circle panel use this tile. Menus, the command palette and the "Show" menu keep the kind icon, because their labels are text. Known limit: Compose apps, live sites, pages and files show the kind icon. Revisit this when the daemon reads app icons.

## 6. Machines and the daemon

- **K-601** Each machine runs one `kitshn` daemon as a service of the user who joined it: a systemd user service on Linux (it starts without a login when the user has lingering on), a launchd agent on macOS. The tunnel runs as a second user service of the same user, `kitshn-tunnel.service` on Linux and `com.kitshn.tunnel` on macOS, which the daemon installs and starts (K-603). The daemon is one binary per platform, so a machine needs no Node.js. The first version has no Windows daemon. A Windows machine stays on the machine map portal until a later milestone ([docs/migration.md](docs/migration.md)).
- **K-602** "Add machine" creates a service token and a remotely managed tunnel, and shows a one-time join command with a code that expires after 10 minutes: `curl -fsSL <address>/join | sh -s -- <code> <address>`. The command downloads the daemon, runs `kitshn join`, and starts the service. `kitshn join` saves the token and the tunnel token in a file that only the daemon user can read, makes the machine key pair and sends its public half with the code (K-1703). kitshn stores the two tokens only encrypted with a key from the code, and deletes them when the code is used. The code has 20 random characters (about 99 bits), so kitshn sets no attempt limit; revisit if codes get shorter.
- **K-603** The daemon runs `cloudflared` for the tunnel of its machine as its own user service (K-601), with the tunnel token in a file that only the user can read (`--token-file`), not on the command line. A restart or an update of the daemon never stops the tunnel, so apps and sites keep serving. The daemon restarts the tunnel service only when `cloudflared`, its token or its service file changes, and reads the state of the service for its status (K-605). Known limit: "running" means that the service runs, not that `cloudflared` has a connection to Cloudflare. Revisit with the readiness endpoint of `cloudflared` when a false "running" misleads. kitshn owns the tunnel ingress through the API; the daemon never edits it. Each ingress rule whose address has a kitshn Access application sets `originRequest.access` with `required: true`, the team name (the first label of `ACCESS_TEAM_DOMAIN`) and the audience tag of that application, so `cloudflared` drops a request without a valid Access JWT ([origin parameters](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/origin-parameters/#access)). This guards the address when a DNS record or a removal step goes wrong. A rule whose application has a Bypass policy (K-403) gets no check, because Access issues no JWT for Bypass. kitshn takes this decision from the application that Cloudflare last accepted, not from the shares, so the check never comes on before Access stops the Bypass. When kitshn does not know the accepted body of the application or of one of its policies, the rule goes without the check. kitshn stores the audience tag of each application. Before it writes ingress, it reads missing tags from the list of applications, and tries again after five minutes. When the list does not have the application, kitshn forgets its id and makes it again. A site never leaves the tunnel for a missing tag: while kitshn does not know the tag, the rule goes without the check, and kitshn logs the address. An empty `ACCESS_TEAM_DOMAIN` has the same effect. The check comes on at the next tunnel write after kitshn stores the tag. Checked on 2026-10-27: a Service Auth policy whose only include is an IP range let a request from that IP in with no login, and Access set `CF_Authorization` on the response. So Access issues a JWT for a network member, and the check stays on. An Allow policy with only an IP range sends the visitor to the login instead; kitshn does not compile networks to Allow (K-402). A service token gets a JWT (K-1004).
- **K-604** The daemon keeps one WebSocket to the Durable Object at `/connect`, with backoff after a failure. Each connection starts with the challenge of K-1704. Liveness uses `ping` and `pong` with the Durable Object auto response, so a ping wakes nothing.
- **K-605** The daemon sends its status on connection and on each change, at most once every 5 seconds. It sends a resource sample (CPU, memory, disk) once a minute.
- **K-606** The Durable Object keeps only the latest sample of each machine, in memory. The daemon keeps 30 days of history on its disk and answers a history request. This keeps the daily writes low (K-1302).
- **K-607** Local sites use Unix sockets. A Compose service listens on `<deployment>/sockets/<name>.sock`, and the tunnel ingress sends its address to `unix:<path>`. Services publish no host ports. Caddy is not needed. The [ingress docs](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/configure-tunnels/local-management/configuration-file/) show `service: unix:/path` for local configuration files. Checked on 2026-10-27: the API accepts `service: unix:/path` in a remotely managed tunnel configuration, and `cloudflared` 2026.10.3, run with the tunnel token, served a request from a Unix socket.
- **K-608** For an app that cannot listen on a socket, the recipe names a port inside its Compose network, and the daemon adds a small socket proxy service. The machine still publishes no host port.
- **K-609** Each machine has labels, for example `docker`, `server`, `arm`, `laptop`. The owner sets one order of all machines.
- **K-610** A job names the labels that it needs. kitshn gives it to the first online machine in the order that has all of them. Without such a machine, the job waits in the queue until its expiry (K-613). A deploy runs only on a machine that has the label `deploy`, so the apps of repos never land on a machine that the owner did not offer for them.
- **K-611** A running app stays on its machine. kitshn never moves it by itself. "Move to <machine>" in the card panel deploys it on the other machine and then removes the old copy.
- **K-612** Commands are jobs too. Built-in commands: restart the daemon, update the daemon, collect diagnostics, run a shell command. A provider adds its own commands (K-707).
- **K-613** A job for an offline machine waits. It has a delivery rule ("when online" or "when online and idle") and an expiry, by default 24 hours.
- **K-614** "Run a shell command" needs `control` on the machine. The member that sends it is in the history. A job that kitshn makes itself, such as a deploy (K-812), needs no member; the `deploy` label is the owner's consent (K-610).
- **K-615** "Remove machine: deletes its token and tunnel" runs at once, without a confirm, and History records it. It deletes its service token, its public key (K-1707), its tunnel, its DNS records and its queue, and closes its connection. Its apps show as stopped with "Deploy elsewhere". A connected daemon then stops and removes its tunnel service and the tunnel token file (K-603). For a machine that is offline at that moment, the tunnel service stays until `kitshn service uninstall` on it.
- **K-616** A whole machine can belong to another person. Example: a second VPS whose card sits in the circle "Her" with `use`, and in the Owner circle with `control`. Its provider shows everything on it to every member with `use`, including the owner's threads there. The owner accepted this.
- **K-617** kitshn names one release: the version of its Worker. The join command, "Update daemon" (K-612) and the deploy workflow download the daemon and the CLI only from that release, `edge-<version>`, and check each file against its `SHA256SUMS`. "Update daemon" in the machine panel and the jobs API take no version from the sender. The rolling `edge` release only serves the bootstrap of a new account. The daemons are gzipped in the release (`kitshn-<os>-<cpu>.gz`), and `SHA256SUMS` names the `.gz` files. The release workflow never deletes an `edge-<version>` release: on a public repository they cost nothing, an old one is the way back, and a machine pinned to it keeps working. Every `edge` release is a pre-release, so none shows as "Latest".

## 7. Local interface for providers (T3 Code)

- **K-701** The daemon listens on a local Unix socket: `$XDG_RUNTIME_DIR/kitshn/kitshn.sock` on Linux, `~/Library/Application Support/kitshn/kitshn.sock` on macOS. On start, the daemon removes an old socket file and makes a new one, with mode 0600 in a folder with mode 0700. A second daemon refuses to start while another daemon answers on the socket. On stop, also on SIGTERM and SIGINT, the daemon removes the file and ends its running shell jobs. For each connection, the daemon reads the user id of the peer: `SO_PEERCRED` on Linux, `getpeereid` on macOS. Bun has no call for this, so the daemon uses `bun:ffi`. The daemon closes the connection unless the peer is the daemon user or is in `localUsers` of `machine.json`, a list of user ids. The list is empty by default, so only the daemon user connects. The daemon reads the list at each connection. A peer whose user id it cannot read, or a list that it cannot read, never passes (K-006). The daemon user changes the list with `kitshn local-users list`, `add <user or uid>` and `remove <user or uid>`. Besides the daemon user, only root reaches the socket: its folder is 0700, and on Linux `$XDG_RUNTIME_DIR` is 0700 too. So `add` accepts only root (uid 0). A client of another user finds the socket through `KITSHN_LOCAL_SOCKET`. The daemon logs each request with the user id of the caller. Planned for `pass` (K-1713): a request that the daemon forwards to kitshn carries that user id, so History can name it. An agent pass goes only to an allowed local user (K-1713). Known limit: only root and the daemon user can connect. Revisit when another user needs the socket: a folder with mode 0711 and a socket with mode 0666, with the peer check as the only guard. Known limit: Bun gives the descriptor of a connection only in its `fd` property, which Bun does not document. Without it, the daemon refuses every peer. So CI compiles `packages/daemon/src/peer.selftest.ts` for linux-x64 and linux-arm64 and runs it, and a Bun upgrade that drops `fd` fails CI, not a machine. `.bun-version` names the one Bun of CI and of the release build. Checked on 2026-10-28: the daemon reads the user id of a client of the same user on macOS, from source and in a compiled `darwin-arm64` binary. CI runs the same test on Linux x64 from source, and the self-test compiled for linux-x64 and linux-arm64. Checked on 2026-10-28: the full compiled `linux-arm64` daemon answers `kitshn status` on the Oracle VPS, and on the VPS root (uid 0) is refused until `kitshn local-users add root`, then answered.
- **K-702** The socket speaks JSON lines: requests with an id, answers with the same id, and events with no id. An error answer to a line without a valid id has the id `null`. The schema is TypeScript types with Effect Schema, in the workspace package `@kitshn/local` (`packages/local`). It is not on npm yet. Revisit when a provider outside this repo imports it (K-704). Providers import the types; the daemon checks each message against them. It answers a bad message with an error that names the problem. A line longer than 65,536 characters ends the connection. The first requests are `status` (the machine id, the key fingerprint, the connection to kitshn, the tunnel service and the version), `rotate-key` (K-1705) and `reconnect` (K-1706). `kitshn status` shows the answer of `status`. When the daemon does not run, each command says so.
- **K-703** The interface pushes events. A provider subscribes once, then gets each change of its resources, grants and commands as an event. Nothing polls.
- **K-704** `register` names the provider, its resource kinds (K-302) and its commands. Each new connection registers again, so a provider restart needs no cleanup.
- **K-705** `upsert` and `remove` add, change and remove resources of the provider's kinds, with a name, a parent, addresses and a status.
- **K-706** For each resource of a provider, the daemon pushes a grant table: each circle with its match mode (K-203), its rules (an email, a domain, an IP range, a service token client id, a machine id) and its passkey flag, with its level and its end date (K-209), so the provider ends the sessions of a member at an end date by itself, also while kitshn is out of reach. The provider decides a level with no call, from the JWT that Access put on the request. The provider saves the revocations that a lower level or an end date needs, runs them again until they work, and runs them after a restart (MM-1306).
- **K-707** The daemon passes a command for a provider as an event. The provider answers with the result. The daemon forwards it to kitshn.
- **K-708** `publishPage`, `publishFile` and `expose` let a provider add a page (section 10), a file, or a live site (K-1104) with one call.
- **K-709** A resource kind can carry a desired state: a JSON value that kitshn stores and pushes to every machine with that provider. kitshn does not read the value. T3 Code uses it for shared settings and themes. Each value is at most 64 KB. A value can hold a shared part and one part per machine; kitshn pushes each machine only the shared part and its own part. A provider may send a JSON Schema of the value with `register` (K-704), so the map edits it with generic controls without knowing the provider.
- **K-710** A local round trip (request to answer) takes under 5 ms, and a change on the map reaches a provider in under 1 second when its machine is online.
- **K-711** The provider holds no Cloudflare credential. Only the daemon holds the machine token and the machine key (K-1702).
- **K-712** T3 Code side: the fork adds the interface in its own files, with one-line hooks in upstream files. It never breaks upstream code paths when the daemon is missing: then T3 Code runs as upstream.
- **K-713** T3 Code adds these kinds through the interface:

  | Kind | Levels | Notes |
  | --- | --- | --- |
  | `t3.app` | view, use, control | The T3 web app, desktop app connection and phone app connection of one machine. Levels map to the T3 scopes `read`, `standard`, `admin` of MM-302. |
  | `t3.thread` | view, send | One thread through upstream guest links. The circle is the guest list. |
  | `t3.agents` | use, exec | What agents on another machine may do on this machine. A machine member of a circle gets it. `use` means agent tools; `exec` adds `kitshn_exec` (MM-1908). |
  | `t3.settings` | none | Shared settings and themes as desired state (K-709). Not shareable; the map hides it. |

- **K-714** The T3 fork MCP tools get new names:

- **K-715** Agents never raise access. An agent change that adds a card to a circle, raises a level, or adds a circle member becomes a proposal for the owner. Changes that lower access apply at once. This keeps MM-803. For agents on a machine, K-1612 applies.
- **K-716** A preset is a saved map layout: the circles, their members and the shares, with a name. Apply a preset from the History view or with `kitshn_preset`. An apply is one revision with Undo, runs the guard of K-105, and follows K-715 for agents.
- **K-717** Each `t3.app` card has the setting "Update channel": `nightly` (a build for each commit) or `daily` (one release a day). Every machine starts on `nightly`. The setting belongs to one card, not to the kind (K-709 holds values for all machines of a kind): kitshn stores it with the card and pushes it only to the provider on that machine. Changing it needs `control` on the card, which kitshn checks when it writes the value; an agent with `control` may change it, because it does not change access (K-715). The owner changes it in the card panel or with `kitshn_set_setting`. The T3 updater uses the new channel from its next update check. Milestone 5 adds the setting; milestone 6 turns it on with the provider.
- **K-718** An agent key is a device member (K-106) without the admin card. Planned (section 17): an agent on a joined machine acts as its machine with passes, and an agent key stays only as an exception that the owner makes (K-1732); from then on, a key calls `kit.<zone>/agent/key/<path>` instead of `kit.<zone>/agent/<path>`. Put it in a circle such as "Agents" and drag in the cards it may manage. Its agent circles are circles of devices only that name it, have not ended and that it matches; a circle with people, domains, networks or Everyone is never an agent circle, and a token without an agent circle gets a refusal. It manages a card that one of its circles holds at the circle level `control` (or a `control` override), before the kind cuts the level down (K-206). With its service token on `kit.<zone>/agent` it sees only those cards, without their machine or group, and its agent circles, with no members, and Everyone when it may publish; it moves those cards, but only between its agent circles at the level `control`, or out of every circle; and it runs jobs on a machine only when it manages the machine card, every card that runs on it and every card that the machine's own token opens (K-107, K-614), never by labels, checked again when a job goes out; a redeploy that it asked for goes out only while the key manages the card, the machine has the label `deploy` and runs the card; it reads the state and output of its own jobs, and the history names it by its member name. It deploys a card it manages in two ways, and never sends code itself (K-812): "redeploy" starts the last build of a Compose app that came up, from the copy that the daemon keeps on the machine, while that machine still has the label `deploy` and still runs the card; "build" runs the repo's own `kitshn.yml` workflow with `workflow_dispatch` on the branch of the environment, through the kitshn GitHub App (K-908) with a token for that repo and Actions only; a preview (`pr-<n>`) gets no such build. A dispatch deploys as a push of that branch. Both ways follow the repo gate (K-819). It never edits circles, members, stacks, levels, the pause or any admin setting. It removes no app and deletes no volume (K-909). Planned: after machine identity lands, it removes only the apps that it added. The owner gives a key two rights on its device member in an agent circle, and both are off by default: "may add apps" lets it allow a waiting repo (K-819), and "may publish" lets it publish a card of a repo that it allowed. Only a member with control on the admin card (K-104) sets them, in the circle editor; each change is a History revision that names the right, the key and the circle. The map shows them as "adds apps" and "publishes" stickers on the device in an agent circle. A publish moves a static site, Worker site or Compose app into the overlap of an agent circle of the key at `control` and the Everyone circle (`POST kit.<zone>/agent/publish` with `{"card": <id>, "public": true}`), so the key keeps managing the card: it still redeploys it, takes it back and runs jobs on its machine. Everyone counts only while it is public, has no other member and matches "any". kitshn refuses a publish that leaves every agent circle of the key at `control`; when no such circle overlaps Everyone, the owner moves the Agents circle alone (K-504) so it overlaps Everyone, and its cards stay in place. A live site is never published. `"public": false` takes the card out of Everyone and keeps it in the same other circles; it needs no "may publish", because it lowers access, but only for a card that the key added. For a card outside Everyone it does nothing. A move with `/agent/apply` follows the same publish rules. This is the one exception to K-715: the owner chose the cards, the circles and the rights, so a move between them raises no access that the owner did not give. The map marks a device that has an agent circle and no admin card with an "agent" sticker.

## 8. Recipes and deploys

- **K-801** A recipe is `kitshn.config.ts` with `export default defineApp({...})`. The value is one object literal. The `kitshn` npm package exports `defineApp` and its types as a `.d.ts` with no imports, so an editor shows recipe mistakes; it has no runtime dependencies, because its CLI is one bundled file. Until it is on the npm registry, an app does not need it: Actions runs `kitshn check` from the release. For editor types, install the `kitshn.tgz` asset of an `edge-<version>` release without saving it (`npm i --no-save <address>`). A later `npm i` removes it again, so an app keeps `kitshn.config.ts` out of its own `tsc` run.
- **K-802** Recipes do not compute. A lint rule in `kitshn check` refuses loops, conditions, function calls other than `defineApp`, and imports other than `kitshn`. The lint rule is enough, because kitshn never runs repo code (K-803).
- **K-803** GitHub Actions reads the recipe without running it: `kitshn check` turns the literal object into JSON. kitshn checks the JSON with the same schema. kitshn never runs repo code. The reusable workflow is `.github/workflows/kitshn2-deploy.yml` in this repo.
- **K-804** Kinds: a Compose app (`compose`), a static site (`static`), a Worker app (`worker`). A recipe has exactly one kind.

  ```ts
  import { defineApp } from "kitshn";

  export default defineApp({
    compose: { runsOn: ["docker", "server"] },
    deploy: [
      { on: "push", branch: "main", name: "prod", address: "riffle.example.com" },
      { on: "pull_request", name: "pr-{pr}", ephemeral: true, startsIn: "Owner" },
    ],
  });
  ```

- **K-805** A static site names a build command and an output folder. Actions builds it and uploads the files. kitshn deploys them as Workers static assets, with no Worker code, so their requests are free ([static assets billing](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)).
- **K-806** A Worker app names its `wrangler.jsonc`. kitshn refuses fields that name a place: `account_id`, `name`, `routes`, `env`, and fixed storage ids. kitshn sets the name, the routes and the storage for each environment.
- **K-807** `deploy` maps triggers to environments as in KitSHn 1: the first matching entry wins. `startsIn` names the circle of a new environment, except for a repo that an agent key allowed (K-819). After that, the map decides (K-518). A `pull_request` entry is named `pr-{pr}`, and the number comes from the signed GitHub token, so a pull request reaches only its own preview. The token of a closed (merged) pull request names no number; then kitshn takes the request's number only to close a preview that the token's own head branch deployed. A push environment deploys only from the branch that first deployed it.
- **K-808** `needs.vars` and `needs.secrets` list names. Values come from the kitshn store, per app and environment. A `KITSHN_<NAME>` GitHub variable or secret forwards into the store as `<NAME>` on each deploy and wins over the store. A deploy fails before any work when a needed name has no value, and it names each missing name.
- **K-809** The kitshn store encrypts secret values with AES-GCM under a Worker secret. The map shows names and "set" or "missing", never a value.
- **K-810** The workflow file is the same few lines for every app. It needs `permissions: id-token: write` and calls the kitshn action.
- **K-811** Deploy auth: Actions sends its GitHub OIDC token (issuer `https://token.actions.githubusercontent.com`). kitshn accepts a token whose `repository_owner_id` is on its list of owners. It refuses any other token. The list holds user accounts only; GitHub organizations are not on it for now.
- **K-812** A Compose deploy is a job (K-610). Actions sends the checkout, with `.git` and without a stored token, and the `KITSHN_*` params to R2 through the Worker, with its OIDC token. The daemon downloads both with its machine token, only while it runs that job. After the app comes up, the daemon keeps that build and its params on the machine as the last good build (K-718), and replaces it only with the next build that comes up. It builds with Compose at the lowest CPU priority and starts the app with the variables of KitSHn 1 (`KITSHN_SOCKET_DIR`, `KITSHN_DEFAULT_SOCKET`, `KITSHN_ENVIRONMENT`, `KITSHN_DATA_DIR`, `KITSHN_LOG_DIR`, `KITSHN_PARAMS_FILE`, with the params quoted as KitSHn 1 quotes them, so Compose still reads a `$` in a value as a variable), so a KitSHn 1 `compose.yml` works unchanged, within the limits of K-818. The daemon takes the Compose files that Compose finds on its own (`compose.yml` and `compose.override.yml`), or the recipe's `file`, and passes them to Compose by name. KitSHn 1 deploy credentials (`KITSHN_SSH_KEY`, `KITSHN_VPS_HOST`) never reach the app. A machine runs one Compose job per app at a time. When the socket answers, the daemon exposes it under the address name (K-1104), so the tunnel, DNS and Access follow the live site path. The files are deleted from R2 when the job ends, and an R2 rule removes any that remain after a day.
- **K-813** The Actions step asks kitshn for the state of the deploy every few seconds until it ends, and prints the job output and the final address. It fails when the deploy fails. The daemon sends the output at the end of the job, not line by line; revisit when builds get long enough to need live logs.
- **K-814** The deploy ends with a route check: kitshn requests the address and records status and content type, as KitSHn 1 does.
- **K-815** `kitshn try` builds and runs a recipe on the machine of the developer with a temporary socket, as KitSHn 1 `try`. It touches no environment.
- **K-816** kitshn creates a GitHub deployment and its status for each environment, with the address.
- **K-817** Planned ([#60](https://github.com/Yarden-zamir/kitshn/issues/60)). A `push` entry may list several addresses; a `pull_request` entry keeps one (K-901). Each address is the apex or one level below a zone of K-1111, so Universal SSL covers it. The first address under `KITSHN_ZONE` is the main one: it keeps the card address, the expose name (K-1104), the route check (K-814) and the deployment (K-816). Every other address either serves the app, with its own ingress to the same socket, DNS record and Worker route on its own zone, or redirects (301) to another address of the environment with a Single Redirect rule on its zone and no ingress (the API token then needs the redirect rules permission). K-402, K-403 and K-410 hold per address: its Access application comes before its DNS record, and removal runs in reverse. kitshn takes over an existing record only as K-1404 says. The data of a moved app: on the same machine the first deploy takes over the KitSHn 1 data folder (K-1404); on another machine the owner stops the old app, copies the data folder, checks the copy, then deploys and moves the DNS record.
- **K-818** A Compose app gets no more than its own folders, project and network. Each deploy or redeploy unpacks the source into a new folder that no running container mounts. There the daemon first parses each raw Compose file as YAML for `include` and `extends`, before Compose reads them; a file that is not one YAML mapping fails the deploy. `extends` needs an allowance also within one file. Then it reads `docker compose config --format json --no-interpolate`, which names the env and label files without reading them, checks those files, and only then reads the config once more with the params. Every Compose command of a deploy that reads Compose files gets them and the params file by name, so the params and the repo's `.env` add no Compose file; the clean-up after a failed takeover runs by project name in the app's folder, which holds no Compose file. The whole check runs before the KitSHn 1 takeover (K-1404), so a refused deploy leaves KitSHn 1 as it is. The recipe's `file` is a path inside the repo, also after symlinks; a missing file fails the deploy. Only a short list of Compose keys passes on its own (image, build, command, environment, env files, volumes, networks, healthcheck, restart, limits, `scale`, `profiles`, `extra_hosts` and a few more), and only with safe values: build contexts, additional build contexts, the Dockerfile, env and label files stay inside the new source folder after symlinks; bind mounts, secret and config files stay inside the app's source, data, log and sockets folders after symlinks, are no link inside those folders (setting `link:<path>`), and a link whose target is missing fails the deploy; and are not under another writable bind source of the app (setting `nested:<path>`), because Docker follows links at each container start; a built image and its tags are `<project>-<service>` with an optional `:<tag>`, and a container name is `<project>-<service>`; logging is `json-file` or `local`; a service joins networks without aliases or addresses; top-level volumes and networks are plain ones of the app's own project, and a network can be `internal`; no label starts with `com.docker.compose.`; `cache_from` names registry images only. Every other key or value, for example `privileged`, `cap_add`, `pid`, `network_mode`, `ports`, `volumes_from`, `provider`, `post_start`, `security_opt`, `include`, `network:kitshn-edge` or `bind:/var/run/docker.sock`, runs only when the owner names that repo and setting on the allow list of the machine in its panel, for example `Yarden-zamir/dozzle bind:/var/run/docker.sock`; an entry holds for every environment of the repo, previews too. The daemon builds and starts from the checked config itself, not from the repo's files. It builds while the old app still runs. Then it stops every container of the app (by its Compose label, orphans too), checks the bind and file paths once more and runs `up`, so no container of the app can swap a path between that check and `up`. A deploy that fails before `up` starts the old containers again and removes its new folder, so the old app runs on. A failure in `up` or later leaves the app down until a deploy or redeploy comes up. When the app answers, the daemon removes the source folders of earlier deploys. The deploy output names each refused setting. The configs hold the params, so they stay in folders that only the daemon user reads; the daemon keeps only the checked config and params of the last `up`, also of a failed one. A preview teardown (K-904) runs `down` with them, and also removes every volume with the app's project label. A removal (K-909) runs `down` with them and keeps the volumes. kitshn sends Compose jobs only to daemons that report the capability `compose-guard`. Known limits, to revisit when a second person deploys apps on a machine: apps on one machine share the BuildKit cache; a root container can leave setuid files or device nodes in its own folders on the host; kitshn sets no default CPU or memory limits; Compose gives each service its name as an alias on every network that it joins, so an app with `network:kitshn-edge` can take the traffic of a service of the same name in another app on that network; an image or container name `<project>-<service>` can match the same name of another project when the names have dashes (the project `app-foo-1-prod` with the service `2-prod-web` gives `app-foo-1-prod-2-prod-web`, also the name of the service `web` of the project `app-foo-1-prod-2-prod`), so one app can replace the image that the other built, or one of the two fails to start; the check of nested binds holds only for the app's own config, so a process outside the app that changes links in the app's folders, or a link inside the `subpath` of a named volume, is not checked; the link check reads the path as the Compose file writes it, so an outside path that the owner made a link into the app's folders is checked only at its real target and needs no allowance. Rootless Docker for the kitshn user is the planned next step against these limits.
- **K-819** A repo that kitshn has never deployed waits. Its first deploy step records it by its GitHub `repository_id`, and the step fails with "waits on the kitshn map". The toolbar shows the count of waiting repos that the owner can allow; a repo of a removed key or a repo that GitHub deleted does not count. The map panel lists each repo with "Allow" and "Block", and every repo also with "Forget". The panel of each card that the repo deployed shows "Deploys" with the same switch; the card matches by the repo id that kitshn stores with each deploy. "Allow" on a repo that waits after a push starts its workflow again on the first pushed branch through the GitHub App (K-908), and the panel names that branch. Allow is a deploy permission, not an access share, so it works during the pause (K-1504) but starts nothing until Resume. Until a start succeeds, the panel keeps the branch with a "Start" button. After a pull request run, the next run deploys. "Block" cuts a repo off at once, also after a rename or a transfer, because the gate keys on the id: every deploy step checks it, the jobs and Compose deploys of the repo that have not finished fail, kitshn deletes their files in R2, the daemon gets no source of the repo, and agent keys cannot redeploy or build it (K-718). A build whose daemon already downloaded the source can still finish on the machine, and a static upload that already started can finish too; the card stays as it was. A blocked repo still tears down its previews and environments. A repo that finished a deploy before the gate existed counts as allowed; a teardown alone does not count. The gate covers deploys, not jobs: an agent key that manages a machine can still run jobs there (K-718). Only a member with control on the admin card (K-104) blocks or forgets. "Forget" works in every state but one: it stops what the repo has under way as Block does, deletes the gate row and writes a History revision, so the next deploy of the repo waits again. kitshn refuses Forget while the repo has cards on the map, so each card keeps its "Deploys" switch; the owner removes them with "Remove app" (K-909) first. kitshn also refuses Forget of a blocked repo until GitHub reports it deleted (below), because a forgotten repo waits again and an agent key with "may add apps" could then allow a repo that the owner blocked; the refusal says to allow it first. With the GitHub App (K-908), the repo list asks GitHub whether each repo id still exists (`GET /repositories/<id>` with each installation) when it opens, at most once per repo per day and with at most 40 GitHub calls per check. The daily run does not ask, because its alarm already spends 40 of the 50 calls of a Free plan request (K-406). A repo is "deleted on GitHub" when every installation answers 404 for its id and one of them holds all repos of the repo's owner. Any other answer, a fault or no App changes nothing. Such a repo shows "deleted on GitHub" with only "Forget", in the repo list and on its cards, and `GET kit.<zone>/agent/state` leaves it out. A deploy step or a build of the repo clears the mark. Known limit: a private repo that moved to an account without the App also reads as deleted, and an App with selected repos only never marks a repo as deleted. Revisit this when kitshn stores the owner id of each repo. It allows too, and so does an agent key with "may add apps" (K-718): it sends `{"state": "allowed"}` to `POST kit.<zone>/agent/repos/<repoId>`. So each login path checks the token that Access sends with it (`Cf-Access-Jwt-Assertion`) against its own application, and the Worker keeps it in its own cookie on `/` (`__Host-kitshn-login-token`, `__Host-kitshn-passkey-token`) for as long as the token lives. The login applications get their own copies of the people rules of every circle with an active page, file or admin share; Access applications of cards keep the people policy. `/login` gets a copy without the passkey check for each such circle, because that step comes first. `/login/passkey` gets a copy with the passkey check for each such circle with "needs passkey". It then deletes the policies "kitshn any login" and "kitshn any login (passkey)" of older bootstraps when no application uses them. A policy goes on a login application only after Cloudflare holds its current body, so a new passkey check is never skipped. While the login applications hold a copy, the Access sync neither changes nor deletes it until the login step lets go of it; after a login step that failed part way, both the earlier and the new copies count as held. So a failing login step never holds back a policy of a card (K-409). The first run after a deploy fails closed: until the next alarm adds the circle policies, no person can log in to pages and files. When someone deletes a login policy in the dashboard, its old id stays until the daily compare, so login updates can fail until then. A failed write shows as an Access warning on the map and waits for the daily retry; the daily compare (K-408) repairs the applications. Milestone 3 tests it.

## 15. History and safety

- **K-1501** Every change makes one revision with the time, the actor (owner device, agent with machine and thread, or kitshn for an expiry) and a summary. A move that joins the newest revision (K-1505) changes that revision instead of making one.
- **K-1502** "Undo" makes a new revision that reverses a revision, by the rules of K-1506. Undo runs the guard of K-105 and the pause check of K-1504. The undo of an app removal also starts the app again, and its result says what it could not start (K-909).
- **K-1503** Revisions older than 90 days and beyond the newest 5,000 are deleted by the daily alarm.
- **K-1504** "Emergency pause" is a big red button, always in the toolbar and in the command palette. One press opens a short confirm that names what stops; its button then pauses. The confirm has one option, "Also close public sites", which is off. Without it the pause keeps the shares of public circles (Everyone, "any must match") on sites, pages and files, so public sites, apps and pages stay up, as in the old portal; a public share of a machine or a repo still closes. With it the pause is a lockdown. The pause moves no card, but stops: every share except the admin share of the Owner circle for its people and, unless it is a lockdown, the shares of public circles, so other sites, Compose apps, live sites, pages and files close; every share of devices, agent keys and machines, so agent keys stop moving, deploying and running jobs (K-718), and the jobs that devices and agent keys queued fail; new deploys from GitHub, which wait until Resume (a preview teardown still runs, and a deploy that already runs finishes behind closed doors, with its card in the tray); and "stop all agents" to every provider that has the command (providers arrive in milestone 5, so today no running T3 agent stops). Pages and files close at once; Access applications close through the alarm queue of K-406, so many applications take a few alarm runs. Machines stay connected and their apps keep running behind closed doors. The owner keeps the admin and the machine commands they had (MM-711), and while paused any change that would raise access is refused; lowering access still works. Every view shows a hazard frame and a red banner with the kind of pause (public sites open, or lockdown), who paused and when (stored with the pause), and "Resume". A pause can become a lockdown with an edit, which keeps who paused first; the history names the kind of each step. Only Resume ends a pause or opens public sites again after a lockdown. A public site, Compose app or live site on a machine stays public in a pause that is not a lockdown. Resume needs a fresh passkey: the owner passes the passkey check of the `kit.<zone>/api/fresh` application (its own cookie path, a session and an MFA session of ten minutes), confirms once more, and only that path ends the pause; the people who can Resume are the owner emails of the bootstrap that are also in the Owner circle; an edit or an undo never does. VERIFY: that the MFA session of ten minutes asks for the passkey again after the 24-hour login of the admin; milestone 6 tests it. Resume returns the shares. Dropped from the machine map: the flip-up cover, sounds and counts popover of MM-708 (the confirm replaces them), the cut wires of MM-717 (circles have no wires), and the T3 lock of MM-718 until K-1618.
- **K-1505** A move joins the revision of the move or drop that started it. A move is a card that goes from one point to another, or a circle whose place alone changes. A drop is a card that comes onto the map, from the tray or by an upload, or a new circle. A move joins the newest revision when that revision is a drop or a move of the same cards or circles (or more), by the same actor, and its last move or drop is at most 2 minutes old. The revision then keeps the first `before` and takes the last `after` of each item, and History shows one entry with the time of the last move. When a move changes a share, the summary is the net summary of the whole revision, because History is the record of who gave access. A move that changes no share keeps the first summary and adds "and moved it" once. The Undo of the toast of a later move (K-503) then takes back the whole revision. The commit on the server does this, so the map, `/api/apply` and agent tools behave the same. Two minutes covers the nudges after a drop; a later rearrangement gets its own entry. Known limit: any other revision in between, also one by another actor or by kitshn, starts a new entry. Revisit this when drops and their moves split on a busy map.
- **K-1506** Undo reverses the caller's own newest revision that changes something, as a whole, and nothing else. An undo and the revision that it undid no longer count, so the next Undo reverses the change before them. The rule is per actor because other actors write often: in a day of the live map, about half of the revisions came from devices, deploys and live site reports, so "the newest revision of anyone" would turn Undo off at random. kitshn refuses an Undo of an older revision, of a revision of someone else, of a whole undo, and of a revision that is undone already. A per-item undo (K-1507) is a normal revision, so Undo can reverse it. kitshn also refuses the undo, and names the later revision, when a later revision by anyone depends on the same things: both touch the same card, or one of them changes a circle that a card of the other is or was inside, also inside a shape of the circle that no longer exists. A revision touches a card when it changes the card's place, stack or share settings, or makes, removes or forgets the card. kitshn forgets a card when a live site stops, a preview closes, a machine goes or a page or file is deleted; the revision of that deletion marks the card, also one that waited in the tray, so an older undo never touches a new card with the same id. Such a revision records an action and has nothing to undo. A revision changes a circle when it changes the circle in any field or a share setting of it. This rule keeps an undo from giving access that a later change made possible, such as a card that entered a circle after a member left it. Undo applies the plain inverse of the revision. The History view shows Undo only on the caller's own newest revision (K-1508). Known limit: a later revocation of the same member through another circle does not block the undo, so the undo can give that member access again through the circle that the revision changed. Revisit this when a circle shares members with another circle often. Known limit: revisions from before the forget marks do not mark the cards that they deleted, so an older undo can still meet a new card of the same id. This ends when those revisions age out (K-1503).
- **K-1507** "Undo the last change" of one card or circle undoes only that item's part of the caller's own newest revision that changed the item: `POST kit.<zone>/api/undo-item` with `{"item": {"kind": "card" | "circle", "id": <id>}}`, or the WebSocket message `undoItem`. A card's part is its place, its share settings, its app and its stack membership. A circle's part is the circle and its share settings, and for a drag by its head (K-504) the cards that sat inside it before the drag and moved with it. The rules of K-1506 hold, with the item's part in place of the revision. kitshn refuses the per-item undo when the rest of the revision depends on the item's part, for example a circle that became public while the card left it: "undo the whole change instead". The undo is a revision of its own, "Undo #<n> for <item>: …", so a second call reverses the first. Only a member with control on the admin card (K-104) calls it, as Undo. Agent keys have no undo (K-718). The context menu of a card and of a circle and the command palette call it as "Undo last change to this card" or "… circle" (K-523). Before it offers the entry, the client asks `GET kit.<zone>/api/undo-item?kind=card|circle&id=<id>`, which answers `{"allowed": true}` or `{"allowed": false, "reason": …}` by the same rule over the whole History and every check that the undo itself runs, so the menu and the undo agree. The one exception is the stop of a removed Compose app that a machine runs now (K-909): it depends on live jobs, so the menu can offer the undo and the undo then refuses, with the reason in its toast. The menu asks once when it opens for a card or a circle, and again when a new revision arrives while it is open. Until the answer comes, the entry is disabled with the tooltip "Checking whether this can be undone", and after 150 ms its label says "checking…"; a quicker answer shows at once. A refused undo then shows disabled with the reason, and an answer for a closed menu or another item is dropped. The palette asks once when it opens, only for the selected card or circle, and offers no per-item undo for other items.
- **K-1508** History groups the revisions by day (today, yesterday, older) and then by runs of one actor, newest first. The actor heads each group once, and each row starts with the verb, from the summary alone, for example "shared tick3d with Everyone at view" or "changed the level of riffle in Her from view to use". A row of kitshn names its reason, such as an expiry, next to its time. A summary of a shape that the rules do not know stays as it is, so a row never adds a fact. Filters: the kind of change (cards, shares, circles, stacks, apps, pause, actions; a share setting that changes or ends counts as a share, also when it takes its card out of a stack), the actor ("Anyone" shows every actor, so the chip is not read as the Everyone circle; every kitshn reason is the one actor "kitshn"), and words in the name of a changed card or circle or in the summary. Only the row of the caller's own newest revision (K-1506) shows Undo. For that row the client asks `GET kit.<zone>/api/undo?revision=<id>`, which answers as `GET /api/undo-item` does (K-1507), when History opens and again when the caller's own newest revision changes or a move joins it (K-1505); the undo itself checks again. Until the answer comes, Undo is disabled with the tooltip "Checking whether this can be undone"; a refused undo shows disabled with the reason. A click on a row pans the map so that the cards and circles of the row show clear of the panel (K-514), and outlines them once; the outline fades and does not repeat (K-513). When none of them shows on the map (gone, in the tray, or of a hidden kind), a toast says so. For this, each revision in the snapshot carries its kind and at most 30 changed cards and circles, from the tag and id of each change and the members of each stack change. Known limit: revisions from before this rule name a new level of a share as a share ("shared … at use"). This ends when those revisions age out (K-1503).

### 17.1 Machine key pairs

Planned, PR 1.

- **K-1701** A machine proves itself to kitshn with its own Ed25519 key pair. Checked on 2026-10-27: Workers `crypto.subtle` supports `Ed25519` for sign, verify, generate, import and export ([Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/)), so kitshn does not need P-256 here. The daemon makes the pair with `crypto.subtle`. Checked on 2026-10-28: a compiled `darwin-arm64` Bun binary signs and verifies, and Bun gives the exact signature of RFC 8032 test 1 (`packages/daemon/src/key.test.ts`). Not yet tested: the compiled `linux-arm64` daemon; the hand install and `kitshn rekey` on the Oracle VPS test it (K-1708), and the panel then shows its fingerprint.
- **K-1702** The daemon keeps the private half in `machine.key` next to `machine.json` (K-602), with mode 0600 in a folder with mode 0700. kitshn stores only the public half, its fingerprint and the time that it became valid, with the machine. The machine panel shows the fingerprint and that time. Known limit: root and every process of the daemon user can read the file, also an agent on the machine. Revisit with a key that cannot leave the hardware (Secure Enclave on macOS, TPM on Linux), or when agents run as their own users.
- **K-1703** `kitshn join` makes the key pair before it sends the join code, and sends the public half with the code to `/join/exchange`. kitshn stores the public half in the same step that deletes the code (K-602). kitshn refuses a join without a public half.
- **K-1704** Each connection (K-604) starts with a challenge. After Access lets the socket in, kitshn sends 32 random bytes, new for each socket, and the fingerprint of the key that it expects (none for a machine without a key; that daemon does not answer, K-1708). It keeps them only in the socket attachment, so a challenge writes no row. The daemon signs four lines: `kitshn-connect-v1`, the kitshn host, its machine id, and the challenge. The host is the hostname without a port: the daemon takes it from the server address in its own `machine.json`, and kitshn from its `KITSHN_HOST`, never from the challenge. kitshn checks the signature with the stored public half. Until the check passes, kitshn reads no message from the socket and sends it no job, state or grant. Another message first, also one that is not JSON, closes the socket. When the check passes, kitshn sends "accepted", and only then does the socket replace an older socket of the machine (4001), so the token alone cannot push the real daemon off. Without a valid answer in 10 seconds, kitshn closes the socket with 4003 and the reason. A replay fails: a recorded answer signs the challenge of an older socket, and each socket accepts one answer only. An answer for another kitshn host names that host, so it fails here too.
- **K-1705** "Rotate key" in the machine panel and `kitshn rotate-key` on the machine do the same thing over the live connection. The daemon makes a new pair and keeps it in `machine.key.next`. It signs five lines with the old private half: `kitshn-rotate-v1`, the kitshn host, its machine id, the challenge of this connection, and the new public half. It sends the new public half and the signature. A daemon that connects in the middle of a rotation signs with the file whose fingerprint the challenge names (K-1704). `kitshn rotate-key` sends `rotate-key` on the local socket (K-702) and waits up to 30 seconds for the new fingerprint. A daemon without a signed connection refuses the request with the reason. kitshn stores the new key, writes a History revision, and closes the connection with 4004 "key rotated". The daemon connects again at once with the new key. From that moment, kitshn refuses every answer that the old key signs. In the panel, only a member with control on the admin card (K-104) rotates.
- **K-1706** "Reset key" in the machine panel is for a key that someone may have stolen, or for an offline machine. For a machine without a key, the same button is "Make key code" and gives only the code (K-1708). kitshn deletes the public half and closes the connection at once with 4005; the daemon then tries again only once an hour. It then shows the command `kitshn rekey <code>`, with the code rules of K-602: one use, 10 minutes, about 99 bits and no attempt limit. The command makes a new pair and keeps it in `machine.key.rekey`, which a rotation or a reconnect never touches. It sends its public half and its machine id with the code to `/join/rekey`; kitshn refuses a code of another machine and keeps that code. After kitshn takes the key, the command moves it to `machine.key` and sends `reconnect` on the local socket (K-702), so the running daemon connects again with the new key. When the daemon does not run, the command says so, and the daemon signs with the new key when it starts. Only that connection changes; the tunnel and the apps keep serving (K-603). Until then the machine cannot connect, so its jobs wait (K-613).
- **K-1707** "Remove machine" (K-615) deletes the public half and closes the connection at once. A rotation, a reset or a removal also makes kitshn refuse every pass that it gave the machine before that moment (K-1715).
- **K-1708** A machine gets its first key only with a key code: from the join (K-1703), or from `kitshn rekey <code>` (K-1706). kitshn never takes a first key from a connection, so nothing runs unsigned. A machine that joined before PR 1 has no key. It connects with its Access service token alone, but only for status: kitshn reads its status and samples, and ignores every other message. It gets no job, also no "Update daemon", and its card shows "needs a key" with "Make key code" in the panel. When the key arrives, kitshn closes the connections of the token alone, and the daemon connects again and signs. Known limits until `kitshn rekey` on a machine without a key: kitshn sends it no job, so deploys and commands wait (K-613), and its apps and its tunnel keep serving. kitshn also ignores its `sites`, `volumes` and `jobResult` messages, so no unsigned message changes routing: offline detection of live sites, `kitshn expose` and late job results wait for the key. Whoever holds the token of such a machine can push its daemon offline (4001) until the rekey. The two joined machines (the Oracle VPS, then the VPS) get the new daemon by hand, because "Update daemon" is a job.
- **K-1709** The machine keeps its Access service token, and `/connect` keeps both locks: Access checks the service token, and kitshn then checks the key signature (K-1704). Access also needs the token on `/connect/deploys/` (K-812), and it stays the Access identity of the machine in circles (K-107, K-1609). The owner chose this on 2026-10-28, on one condition: joining stays one code. kitshn makes the service token and the daemon stores it with the join (K-602); nobody makes or copies a token by hand. With the token, Access drops a socket without a valid service token of the account before it costs a Worker request. The count of service tokens (K-1301) stays one per machine.

### 17.2 Agent passes

Pending: the owner decides between this issuer design and a simpler path, in which the daemon relays the action over its signed connection (K-1704) with no JWT, JWKS or discovery document. Nothing in 17.2 gets built before that answer.

Planned, PR 2. It needs the local socket of K-701.

- **K-1710** kitshn is an OpenID issuer for agent passes, with the issuer `https://kit.<zone>`. The Worker serves `/.well-known/openid-configuration` and `/.well-known/jwks.json` on the kitshn host with no login (K-1204), with `Cache-Control: public, max-age=300`. The discovery document names the issuer, `jwks_uri`, `id_token_signing_alg_values_supported` `["ES256"]`, `response_types_supported` `["id_token"]`, `subject_types_supported` `["public"]` and the claims of K-1712. It has no authorization endpoint, because kitshn gives passes only to daemons.
- **K-1711** The pass key is an ES256 (P-256) key, because more outside OIDC verifiers accept ES256 than EdDSA. It is the Worker secret `PASS_SIGNING_KEY`, a private JWK with a `kid`. The bootstrap cannot make it with only `curl`, `sh` and `jq` (K-1203), so the Worker makes it: when the secret is missing, the alarm makes a pair with `crypto.subtle` and writes the secret through the Workers API. "Rotate pass key" in Settings does the same with a new `kid`. The Durable Object keeps the public half of each old key with the time that it retired. The JWKS lists an old key, and the Worker accepts its passes, for 6 minutes after that time: 5 minutes of pass life and 1 minute of leeway. Then kitshn drops the key. A second bootstrap run keeps the secret (K-1205). VERIFY: a Worker writes its own secret through the API, and its Durable Object keeps its state across the new version; PR 2 tests it.
- **K-1712** A pass is a JWT with `alg` `ES256` and these claims: `iss` `https://kit.<zone>`; `aud` `https://kit.<zone>/agent`; `sub` `machine:<machine id>`; `act` `{"sub": "<provider>:<thread id>"}` when the agent names a thread; `kitshn_action`, one action of K-1716; `kitshn_target`, one card id or one repo id (none for `state`); `iat`; `exp`, 5 minutes after `iat`; and `jti`, 128 random bits. One pass is one action on one target, once.
- **K-1713** An agent asks for a pass with `pass` on the local socket (K-701): the action, the target and an optional thread. `kitshn agent <action> <target>` asks and then calls kitshn in one step. The daemon gives a pass only to an allowed local user, with the peer check of K-701. The daemon sends the ask over its signed connection (K-1704). kitshn answers with the pass, with "waiting" (K-1722), or with a refusal and its reason. Known limit: every process of an allowed local user can ask, so the unit of trust is the machine, not the agent. Revisit when agents run as their own users.
- **K-1714** kitshn gives a pass only when all of these hold now: the machine exists, the machine has the right for the action (K-1716, K-1730), the right is "automatic" (K-1721), and kitshn is not paused (K-1504).
- **K-1715** The agent sends the pass as `Authorization: Bearer <pass>` to `kit.<zone>/agent/<action>`. `/agent` has an Access Bypass policy, as `/deploy` has (K-1204), so the Worker checks the pass itself. It checks the signature with a key of K-1711, `alg` exactly `ES256`, `iss`, `aud`, and `exp` and `iat` with 1 minute of leeway. It also checks that the path and the target in the body match `kitshn_action` and `kitshn_target`. The Durable Object then checks the rest at use time:
  - It stores the `jti` until `exp` plus the leeway, and refuses a `jti` that it has already, so each pass works once.
  - The machine still exists, and its key did not change after `iat` (K-1707).
  - The machine still has the right through its circles, and K-718 and K-819 still allow the action on that target.
  - kitshn is not paused (K-1504), and `iat` is later than the last "Sign out everywhere" (K-110).

  Each failure refuses with the reason (K-006). The daily alarm deletes expired `jti` rows, so a pass costs about two row writes and no alarm of its own (K-1302). Known limit: a pass is a bearer token for 5 minutes, and whoever sends it first uses it. Revisit with a proof of the machine key on each call ([DPoP, RFC 9449](https://www.rfc-editor.org/rfc/rfc9449)).
- **K-1716** The actions match the paths of K-718: `state` reads the cards and rights of the machine; `apply` moves one card; `publish` publishes or unpublishes one card; `allow` allows one waiting repo (K-819); `deploy` redeploys or builds one card; `job` runs one command on one machine (K-612); `job-read` reads the state and output of one job that the machine sent. `state` and `job-read` need no right. Each other action needs one right of K-1730.
- **K-1717** History (K-1501) names the machine, the thread when the pass has `act`, the action and the target. For an approved proposal (K-1723), it also names the approver.

### 17.3 Per-right mode

Planned, PR 3. It needs the Inbox (K-1607), and Web Push (K-1606) for the push.

- **K-1720** Each agent right of a machine (K-1730) has one of three modes: off (the default), "automatic" and "ask me". The owner sets the mode on the machine chip in the agent circle. Only a member with control on the admin card (K-104) sets it, and each change is a History revision that names the right, the machine and the circle.
- **K-1721** With "automatic", kitshn gives the pass at once (K-1714).
- **K-1722** With "ask me", kitshn gives no pass. It makes a proposal in the Inbox (K-1607) that names the machine, the thread, the action, the target and the reason "ask me". It sends a Web Push (K-1606). "Ask me" ships with the Inbox first and Web Push later (decided 2026-10-28), so until Web Push ships in milestone 6, the Inbox count is the only signal. It answers the daemon with "waiting" and the proposal id. The daemon tells the agent. `kitshn agent` waits for the local socket event of the result (K-703), so nothing polls.
- **K-1723** An approve needs a fresh passkey, as Resume does (K-1504). The owner passes the check of `kit.<zone>/api/fresh` within 10 minutes, and only `POST /api/fresh/approve/<proposal id>` approves. A service token never approves. The approve runs the action at once, with the use-time checks of K-1715 at that moment, so a right that the owner took away meanwhile still refuses. kitshn sends the result over the machine connection, and the daemon gives it to the agent. An offline machine gets the result from its queue (K-1608).
- **K-1724** A reject, and an expiry after 24 hours (K-1607), reach the agent in the same way: "refused" or "expired", with the proposal id.

### 17.4 Rights move to machines

Planned, PR 4, after PR 3 works end to end (K-1741).

- **K-1730** Agent rights belong to machines. The agent circles of a machine are the circles of devices and machines only that name the machine and have not ended. K-718 holds for a machine in its agent circles, with the machine in place of the key. The rights are "adds apps" (K-819), "publishes" (K-718), "runs commands" (jobs on a machine that it manages, K-718, K-1612), and later "removes apps it added" (planned K-909, not yet in this spec). The map shows the stickers on the machine chip, with a mark for "ask me".
- **K-1731** A machine in an agent circle is also an Access member of that circle (K-107), so its service token opens the sites of the circle. This is the rule of K-1612: an agent on a machine acts as its machine.
- **K-1732** An agent key (K-718) is only an exception that the owner makes, for an agent that runs on no joined machine. Existing keys keep their rights. The map marks each key with an "exception" sticker. From PR 2, keys call `kit.<zone>/agent/key/<path>`, an Access application with the machines policy, because `/agent` takes passes only. Access applies the more specific path ([application paths](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/app-paths/)). VERIFY: this holds for two separate Access applications; PR 2 tests it. This changes the address for current key clients.

### 17.5 Budget and test plan

- **K-1740** For the reference setup (K-1301) with about 300 agent actions a day, section 17 adds about: 350 Worker requests (300 pass uses and at most 50 discovery and JWKS fetches; kitshn checks passes with its own key, so it fetches no JWKS itself); 320 Durable Object requests (300 uses, and about 15 for 300 asks at the WebSocket ratio of 20:1); and 650 rows written (600 for `jti` rows, one write and one delete each, and about 50 for proposals and key changes). Challenges write no row (K-1704). The revisions of agent actions count with shares and revisions. Every daily limit stays under 10%. [docs/architecture.md](docs/architecture.md) holds the table.
- **K-1741** The end-to-end test runs from the Oracle VPS through the owner's `machine_exec` tool, after PR 3:
  1. The Oracle card shows a fingerprint and no "needs a key" sticker. A reconnect of the daemon passes the challenge.
  2. The owner puts the Oracle machine in an agent circle at `control`, with "adds apps" and "publishes" set to "automatic". The machine also gets "runs commands" on itself.
  3. The agent makes a repo from a template, with a recipe, and pushes. The first deploy step fails with "waits on the kitshn map" (K-819).
  4. `kitshn agent allow <repo id>` starts the waiting branch. The new card lands in the agent circle.
  5. `kitshn agent deploy <card>` redeploys the card, and `kitshn agent publish <card>` makes it public. A request with no login gets status 200.
  6. The owner sets "publishes" to "ask me". `kitshn agent publish <card> --private`, then `kitshn agent publish <card>`, answers "waiting" with a proposal id. The push arrives. The owner approves with a fresh passkey. The agent gets the result, and History names the machine, the thread, the action and the approver.
  7. A second proposal that the owner rejects, and one that expires, tell the agent "refused" and "expired".
  8. Refusals: the same pass a second time, a pass after its expiry plus leeway, an ask from another user (`sudo -u nobody`), an ask during a pause, and a pass from before "Rotate key".
